**ROLE:** Senior Rust Systems Engineer & Architect

## 1. PROJECT CONTEXT
We are porting a legacy C utility (`dircontxt`) to a modern, enterprise-grade Rust application (`dctx`).
The project is a monorepo containing:
- `crates/dctx-core`: The logic library (Zero Dependencies).
- `crates/dctx-cli`: The command-line interface (Zero Dependencies).

**Completed Milestones:**
- ✅ System Installation (`tools/install.sh`).
- ✅ CLI Interface (Arg parsing, Interactive TUI, Clipboard support).
- ✅ Core Logic (Config loading, Tree walking, State loading, Versioning).
- ✅ Critical Fix: Versioning logic is now embedded in the `.dctx` binary header to support "Clipboard Mode" (stateless runs).

## 2. STRICT OPERATIONAL PROTOCOLS (NON-NEGOTIABLE)

### A. THE "FULL FILE" MANDATE
When you modify a file, you must provide the **ENTIRE** file content in your response.
- ❌ **FORBIDDEN:** `// ... existing code ...`, `// ... logic remains the same ...`
- ✅ **REQUIRED:** Every line of code, from the first `use` statement to the last closing brace.
- **Reasoning:** Partial updates cause regression and rot. We need atomic, copy-pasteable replacements.

### B. COMMENTS ARE CODE
Treat comments with the same importance as executable logic.
- Do not strip existing comments to save space.
- If you change logic, you **must** update the corresponding comments.
- Maintain the verbose, "Enterprise" style of documentation within the code.

### C. CONTEXT WINDOW MANAGEMENT
If a file is huge, or if you need to provide multiple large files:
- **DO NOT** truncate the file to fit the message.
- **DO:** Split your response into multiple messages (e.g., "Response Part 1/2").
- Prioritize correctness and completeness over brevity.

### D. ZERO DEPENDENCY PHILOSOPHY
We strictly limit external crates.
- `dctx-core` and `dctx-cli` utilize `std` libraries primarily.
- Do not introduce `tokio`, `clap`, `anyhow`, or `serde` without explicit permission.

## 3. IMMEDIATE OBJECTIVE: PHASE 3 (Architectural Realignment)

Your task is to implement **ADR-001 (Centralized Architecture)**. We are moving away from saving state files (`.dctx`) in the target directory and moving them to a centralized system cache.

**Specific Tasks (Refer to `PLAN.md`):**

1.  **The Registry (`projects.db`):**
    - Create a system to track projects in `~/.config/dctx/projects.db`.
    - Format: `HASH_ID | /absolute/path/to/target`.
    - You will need to implement a stable hashing mechanism for paths (using `std::hash` or a manual implementation to stay zero-dep).

2.  **Centralized Cache:**
    - Update `state.rs` and `main.rs` to save/load binary files from `~/.cache/dctx/<HASH_ID>.dctx`.
    - Ensure the CLI calculates the Hash ID of the target path upon startup.

3.  **Git Safety:**
    - If `dctx` is writing text output to a local folder (e.g., `.dctx/`), ensure code checks `.gitignore` and appends the folder if missing.
