# Which engine does the offline wheel install run?

The strongest byte comparison ends at the wheel ZIP. The offline fixture compares its executable member with the input CLI, then installs from a disposable wheelhouse and runs a client inside a fresh venv. The archive that CI made, the wheel pair it uploads, and the installed executable that answered the client have no single identity check connecting them. This is a source and fixture audit. No CI run, registry entry or released artifact was sampled.

## Native archive to wheel

**1. The archive and wheel have a common input. Confidence high.** The wheel workflow calls the release recipe, which builds the target CLI, runs its version command and passes that file to the archiver. Unix targets get a tar.gz with a root member named `dctx`. Windows gets a ZIP with `dctx.exe`. Each also contains `LICENSE` and `NOTICE`. The wheel step separately opens the loose Cargo executable. It never opens the archive produced under `target/python-native`. A swapped archive or an archiver that altered the payload could pass the wheel checks. The tagged release also invokes the recipe in a separate job, and its attestation subjects are native archives. A wheel built on a different run has no demonstrated equality to that release. (`tools/release/build.sh:40`, `tools/release/supply-chain.py:40`, `tools/release/supply-chain.py:61`, `.github/workflows/python-packages.yml:113`, `.github/workflows/python-packages.yml:119`, `.github/workflows/release.yml:127`, `.github/workflows/release.yml:186`)

The archive-side test is `ReleasePayloads.test_archives_ignore_host_mtime_mode_and_location`. It asserts the exact three names and reproducibility across five targets using the same synthetic input. `test_seal_all_platforms_and_detect_tampering` compares the loose member in the air-gap bundle with that input. On the wheel side, `WheelTests.test_offline_binary_extra_installs_and_runs_without_source_or_network` compares the first executable basename it finds in its wheel with the loose input, and checks mode 0755. Neither test compares the two independently opened archive members. (`tools/release/test_supply_chain.py:27`, `tools/release/test_supply_chain.py:31`, `tools/release/test_supply_chain.py:84`, `packages/python/tests/test_wheels.py:89`, `packages/python/tests/test_wheels.py:102`)

**2. The builder checks the input architecture. The finished wheel's platform claim has partial coverage. Confidence high.** Before packaging, the builder checks the Python version declaration against the engine manifest and repository version, validates the binary header, then runs that CLI's RPC hello and requires id 0, the exact engine version and protocol major 1. It stores the bytes it read under the target's module name. The writer takes the same tag tuple for the filename (dot-compressed for multiple tags) and the individual `Tag: py3-none-…` lines in `WHEEL`. The wrapper uses `py3-none-any` and purelib true, the native wheel purelib false. (`packages/python/tools/build_wheels.py:69`, `packages/python/tools/build_wheels.py:79`, `packages/python/tools/build_wheels.py:92`, `packages/python/build_backend.py:42`, `packages/python/build_backend.py:85`)

| Target | Platform part of filename / tags after expansion | Expected member and input check |
| --- | --- | --- |
| Linux musl, x86_64 or aarch64 | `manylinux_2_17_<arch>` and `musllinux_1_2_<arch>` | `dctx_binary_linux_<arch>/dctx`, little-endian ELF64, machine 62 or 183 respectively, rejects PT_INTERP and DT_NEEDED |
| Linux GNU development, same architectures | `linux_<arch>` | Same module and ELF machine checks, no static-link requirement |
| macOS Intel | `macosx_10_13_x86_64` | `dctx_binary_darwin_x86_64/dctx`, little-endian Mach-O 64, CPU 0x01000007 |
| macOS Apple Silicon | `macosx_11_0_arm64` | `dctx_binary_darwin_aarch64/dctx`, little-endian Mach-O 64, CPU 0x0100000C |
| Windows x64 | `win_amd64` | `dctx_binary_windows_x86_64/dctx.exe`, MZ and PE signatures, machine 0x8664 |

The mapping and header checks are at `packages/python/tools/build_wheels.py:22`, `packages/python/tools/build_wheels.py:33` and `packages/python/tools/build_wheels.py:55`. `WheelTests.test_builder_rejects_wrong_architecture_and_false_portability` exercises a wrong ELF machine and an injected PT_INTERP on Linux, plus a manifest version mismatch. It has no DT_NEEDED-only case or equivalent Mach-O/PE negative case. The install fixture exercises pip's acceptance on the runner. It does not independently expand the filename tags, parse the internal tag set, or require exactly one executable at the target-specific path. A wrong additional portability tag or duplicate executable could escape those assertions. Neither the header checks nor the five current-runner jobs establish execution at the advertised minimum OS/libc versions. (`packages/python/tests/test_wheels.py:67`, `packages/python/tests/test_wheels.py:103`, `.github/workflows/python-packages.yml:69`, `.github/workflows/python-packages.yml:86`)

## Metadata and installation receipts

**3. The writer hashes every entry it creates. Only the wrapper's listed rows get independently recomputed. Confidence high.** For both wheels, the backend writes CSV rows with the member path, unpadded URL-safe base64 SHA-256 of the uncompressed bytes, and decimal byte length. It adds one self-row for RECORD with empty hash and size. `WheelTests.test_wrapper_wheel_and_sdist_are_reproducible_and_have_verified_records` reads the wrapper rows back and checks each listed hash and size, including the blank fields if it encounters the self-row. It also checks a second wrapper build and an unpacked-sdist rebuild for byte equality. It never compares the row inventory with the ZIP inventory. A missing row, duplicate valid row or absent self-row can satisfy the loop. The native fixture reads the engine bytes and permissions directly, without reading native RECORD. A wrong native engine digest or size therefore has no independent assertion. (`packages/python/build_backend.py:48`, `packages/python/build_backend.py:61`, `packages/python/tests/test_wheels.py:32`, `packages/python/tests/test_wheels.py:42`, `packages/python/tests/test_wheels.py:64`, `packages/python/tests/test_wheels.py:103`)

The wrapper declares five exact-version dependencies selected by OS, machine and the binary extra. The backend checks the pins and emits the extra condition. The wrapper test counts five `Requires-Dist` lines and looks for the extra condition somewhere in METADATA. It does not compare the full set of names, versions and markers or check the native distribution identity. The single compatible candidate in each fixture exercises positive selection on that host. A second incorrectly applicable marker or a nonmatching marker on an untested machine needs an independent metadata check. (`packages/python/pyproject.toml:18`, `packages/python/build_backend.py:28`, `packages/python/build_backend.py:78`, `packages/python/tests/test_wheels.py:50`, `packages/python/tests/test_wheels.py:125`)

**4. The installer runs a working venv-local engine. Its exact origin and installed digest remain unmeasured. Confidence high.** The offline test creates a fresh venv and a local wrapper/native wheel pair. Its isolated interpreter runs pip with the exact extra/version, local find-links, no index or cache, and a Python audit hook rejecting socket connect, lookup and bind. A second isolated interpreter checks that the imported wrapper and resolved engine are under the venv prefix. It calls `Client.languages()` and compares stdout with the input CLI's `languages --json`, requiring empty stderr. After uninstalling the named native distribution it requires client construction to fail with the local install hint. The CI engine-required test guards against the fixture silently skipping for an unset input binary. (`packages/python/tests/test_wheels.py:88`, `packages/python/tests/test_wheels.py:107`, `packages/python/tests/test_wheels.py:115`, `packages/python/tests/test_wheels.py:127`, `packages/python/tests/test_wheels.py:145`, `packages/python/tests/test_parity.py:76`, `.github/workflows/python-packages.yml:84`)

The fixture reads neither pip's selected wheel filename/hash nor the native distribution's installed RECORD. A different venv-local engine with the same version and language list would meet the path and output assertions. The client resolves its executable and gives that absolute path to `Popen` as the RPC program. The test never equates that path and its digest to the installed distribution's recorded member and the wheel ZIP bytes. The Python socket guards cover the pip interpreter and the specified wrapper socket APIs. They do not trace the native child's network calls. (`packages/python/tests/test_wheels.py:125`, `packages/python/tests/test_wheels.py:133`, `packages/python/tests/test_wheels.py:138`, `packages/python/src/dctx/_client.py:51`, `packages/python/src/dctx/_binary.py:93`)

**5. PATH and DCTX_BIN have different contracts. Confidence high.** The resolver takes an explicit argument first, then DCTX_BIN, then the installed platform module's adjacent executable, then a versioned cache. It restricts the module search to the wrapper's install roots and has no PATH lookup. A set DCTX_BIN deliberately controls selection and a broken override fails. The offline test removes DCTX_BIN, isolates the cache and inherits PATH. It demonstrates default discovery with the override absent. It plants no PATH decoy. `test_explicit_then_environment_are_authoritative` covers override precedence and failure. `test_wheel_before_cache_and_broken_wheel_is_not_hidden` covers cache precedence. `test_platform_module_is_never_taken_from_working_directory` covers Python import shadowing. These unit tests do not exercise a PATH competitor against the installed wheel. (`packages/python/src/dctx/_binary.py:69`, `packages/python/src/dctx/_binary.py:108`, `packages/python/tests/test_parity.py:60`, `packages/python/tests/test_transport.py:65`, `packages/python/tests/test_transport.py:75`, `packages/python/tests/test_transport.py:111`)

**6. CI uploads a different build invocation's output. Publication is pending in the repository. Confidence high about workflow scope.** Five target jobs build into `wheelhouse`, run test discovery, then upload `wheelhouse/*.whl` as Actions artifacts. The offline test constructs its own temporary wheelhouse with a fresh build. A green job would show that the fixture pair installed on that runner. It supplies no install receipt for the exact ZIPs selected for upload. The workflow has read-only repository permissions and ends with artifact upload. The package guide directs users to local wheel files and describes PyPI publication as pending. Registry availability, project ownership and a published digest are outside the evidence collected here. (`.github/workflows/python-packages.yml:16`, `.github/workflows/python-packages.yml:68`, `.github/workflows/python-packages.yml:125`, `.github/workflows/python-packages.yml:128`, `packages/python/tests/test_wheels.py:100`, `packages/python/README.md:10`)
