## 2. Artifact contract: exact existing fields, unresolved formats explicit

The manifest admits exactly five triples (`crates/dctx-plugin-distribution/src/domain/names.rs:161`, `:178`). These are candidate build targets, not supported execution platforms.
For every qualified target, the local release inventory must contain the following; target directories and CLI/checksum/SBOM sidecar names are proposed packaging, not an existing schema:

| Target | Single CLI executable, bundled Git worker linked | Standalone plugin native file |
|---|---|---|
| `aarch64-apple-darwin` | `cli/<target>/dctx` | `dctx-plugin-git-<git-version>-aarch64-apple-darwin` |
| `x86_64-apple-darwin` | `cli/<target>/dctx` | `dctx-plugin-git-<git-version>-x86_64-apple-darwin` |
| `x86_64-unknown-linux-gnu` | `cli/<target>/dctx` | `dctx-plugin-git-<git-version>-x86_64-unknown-linux-gnu` |
| `aarch64-unknown-linux-gnu` | `cli/<target>/dctx` | `dctx-plugin-git-<git-version>-aarch64-unknown-linux-gnu` |
| `x86_64-pc-windows-msvc` | `cli/<target>/dctx.exe` | `dctx-plugin-git-<git-version>-x86_64-pc-windows-msvc.exe` |

CLI output comes from Cargo's `dctx-cli[.exe]`, renamed as current CI does; standalone target is `dctx-plugin-git` (`.github/workflows/release.yml:47`, `:56`; `plugins/dctx-plugin-git/Cargo.toml:12`). Version axes are independent: current CLI 0.25.0, Git plugin 1.0.0 (`crates/dctx-cli/Cargo.toml:3`; `plugins/dctx-plugin-git/Cargo.toml:3`).

Required common/plugin files and fields:

- `plugin.json`: `manifest_version=1,id,name,version,release_sequence,publisher_key,license,protocol,host_api,hooks,commands,capabilities,config,limits,reason_codes,diagnostic_codes,artifacts`; optional `state_version`. No additional top-level fields (`crates/dctx-plugin-distribution/src/domain/manifest.rs:20`).
- `artifacts[]`: `target,file,bytes,sha256,format="native-executable",min_os,runtime_resources`; optional `libc={name:"glibc",min_version}`. Each runtime resource is `{file,bytes,sha256}`. Bytes are positive; hashes lowercase 64 hex; targets and case-folded payload names unique (`crates/dctx-plugin-distribution/src/domain/manifest.rs:25`, `:132`, `:143`, `:174`). Linux libc floors must be measured and emitted even though the parser makes `libc` optional.
- Nested manifest shapes: `protocol[]={major,min_minor,max_minor}`, `host_api={major,min_minor}`, hooks `{name,version}`, commands `{alias,verbs,output,allow_text}` with outputs `{name,fields}`, capabilities `{required,optional,outputs,network:[]}`. Config/limits/code dictionaries must follow their existing referenced schemas; do not synthesize semantics from Rust's shallow parser (`docs/design/plugin-api/manifest.schema.json:14`). Bundled capability values/limits already exist at `crates/dctx-cli/src/plugin/bundled.rs:15`; they are inputs to cross-check, not a second independently maintained permission template.
- `plugin.json.sig`: 64 raw bytes, manifest domain above; key stays outside artifacts. A TEST signature is usable only with the isolated TEST trust root (`crates/dctx-plugin-distribution/src/domain/signature.rs:10`).
- `SHA256SUMS`: exactly the manifest's executable/runtime payloads, across all its targets, one `<hex>  <safe-filename>` per row. The parser also admits `<hex> *<filename>`, refuses duplicates/extras/mismatches and caps at 65,536 bytes. It is not a checksum list for CLI/SBOM/provenance/index (`crates/dctx-plugin-distribution/src/domain/sums.rs:12`, `:16`).
- `LICENSE`, `NOTICE`, `provenance.json`: existing reserved ancillary filenames, not executable/runtime resources (`crates/dctx-plugin-distribution/src/domain/manifest.rs:18`). Resolve actual dependency licences from the built closure; current hash/verifier/plugin manifests say Apache-2.0, superseding older trust-dossier inventory claims (`crates/dctx-hash/Cargo.toml:5`; `crates/dctx-ed25519/Cargo.toml:6`; `plugins/dctx-plugin-git/Cargo.toml:6`).
- SBOM per target/profile and provenance record: **no release SBOM/provenance field schema or generator exists in the inspected release path**; `provenance.json` is a reserved name, not a defined record. SPDX vs CycloneDX, provenance format and CLI-containing release envelope require the REL-C decision packet below. Do not invent field lists and call them implemented. Native/system/SDK/linker and enabled feature closure must be inventoried alongside Rust packages; Cargo.lock alone is not an SBOM.
- Proposed separate `CLI-SHA256SUMS` and containing-release envelope authenticate the CLI, embedded Git inventory, SBOM and provenance after final build. Their format/fields remain REL-C decisions. Frozen `plugin.json` has no fields to authenticate these sidecars, and its checksum mirror refuses extras. Auxiliary metadata needs its own approved domain or authenticated digest linkage (`docs/design/PLUGINS.md:334`).
- `index.json` plus `index.json.sig`: sign the **entire exact index**, not an isolated release row. Top level `{schema:1,sequence,plugins}`; plugin `{id,repository,summary,publisher_key_fingerprint,releases}`; release `{version,release_sequence,manifest_url,manifest_sha256}`. `manifest_sha256` hashes the exact signed manifest bytes. Index and publisher signatures remain independent (`crates/dctx-plugin-distribution/src/domain/index.rs:21`, `:78`; `tools/plugin-index/src/domain/index.rs:55`; `plugins/index/index.schema.json:15`, `:34`).

Optional but needed for offline smoke: `<name>-<version>-<target>.dctx-plugin` contains exact manifest/signature, selected native artifact and declared runtime resources, optionally existing ancillary files. Layout: `DCTXPLG1`, little-endian u32 table length, `{schema:1,entries:[{name,bytes,sha256}]}`, concatenated bytes (`crates/dctx-plugin-distribution/src/domain/bundle.rs:16`, `:44`, `:106`).
Current installer rejects undeclared entries other than its six reserved release names; a separate SBOM file or arbitrary trust bundle cannot simply be inserted. Keep SBOM outside the container until a separately owned contract change is approved; never declare it as a runtime resource to bypass this rule (`crates/dctx-plugin-distribution/src/service/install.rs:204`; `crates/dctx-plugin-distribution/src/domain/manifest.rs:18`).
Use a manifest listing all candidate release payloads with globally unique names and its complete checksum mirror; each offline bundle carries only its selected target. Index schema has no target field: omitting unsupported platform artifacts and gating promotion must occur before signing the candidate index.

## 3. An honest reproducibility claim

Today there is no demonstrated reproducible PL-REL build. No root toolchain pin was found in the tracked-file inventory; release CI explicitly selects floating stable and latest runners (`.github/workflows/release.yml:18`, `:36`).
Proposed claim: **two clean builds on independent paths for the same pinned target and inputs produce identical unsigned payload/metadata bytes**. Record failures rather than normalizing differences away. Cross-OS or cross-architecture binary equality is not the claim.

1. Pin an exact maintained Rust release, target standard-library components, runner image/OS, compiler/linker/SDK, libc and packaging utilities; pin CI actions by reviewed revision. REL-C/Eris selects versions after lock/MSRV validation. A Rust pin alone does not pin native tools.
2. Build exact packages/bins with explicit profile/target/features: `cargo build -p dctx-cli --bin dctx-cli --release --locked --offline --target <triple>` (defaults include `git-worker` and runtime); separately `cargo build -p dctx-plugin-git --bin dctx-plugin-git --release --locked --offline --target <triple>`. Strict CLI is a separate profile using `--no-default-features --features strict`; never substitute it for default bundled Git evidence (`crates/dctx-cli/Cargo.toml:7`). These commands are future authorized runner work, not run here.
3. Commit/refresh lockfiles through their designated CI owner first; refuse `--locked` failures, missing caches and implicit lock updates. Isolate tool workspaces as plugin-index already does (`tools/plugin-index/Cargo.toml:9`). Preprovision caches/targets with separate permission; release preparation never fetches or uses `--pull`.
4. Set `SOURCE_DATE_EPOCH` to the recorded source commit time; propagate it to metadata/archive generation. It does not automatically make rustc, linkers or all dependencies deterministic. Set stable locale/timezone, input ordering, permissions, archive owner/group/mtime and compression options; suppress wall-clock/host-path fields from reproducible documents. Retain observations/receipts separately.
5. Remap each checkout/build/dependency source prefix to stable virtual paths with `--remap-path-prefix`, preserving required Cargo flags. Pin build roots, profile/debug/strip settings and target CPU/features; never `target-cpu=native`. Test remapping by building in two different directories; merely supplying the flag is insufficient.
6. Compare unsigned executable, canonical generated manifest, checksum, deterministic SBOM/provenance and container hashes using dctx-hash. Include actual tool versions, source/lock/recipe digests and flags in the selected provenance format once REL-C defines it. Check dependency build scripts for clocks, paths, random IDs and host probes.
7. Keep notarization, timestamped platform signing, approval receipts, test-key randomness and publication timestamps outside the byte-equality boundary. macOS linker UUID/ad-hoc signature behavior and Windows PE/PDB paths/timestamps require measured pinned-linker experiments; do not assume `SOURCE_DATE_EPOCH` controls them. Real Ed25519 is deterministic only for the same key/message; that says nothing about build reproducibility or secret safety.
8. Avoid self-reference: a CLI cannot embed its own final SHA-256. Embed immutable plugin identity/version/capabilities, then authenticate the completed CLI digest and embedded inventory through the separately verified containing-release envelope. Do not bake a final CLI hash into code or call fixture hashes provenance (`crates/dctx-template/src/plugin.rs:433`; `docs/design/PLUGINS.md:374`).

Verification split:

| Environment | Can verify in an authorized implementation packet | Cannot establish from that environment alone |
|---|---|---|
| This Mac, observed `uname -sm` = Darwin arm64; `sw_vers` = 26.6.2 / 25G83 | Static fields/closures; offline fake transactions; two native arm64 unsigned builds and comparisons if toolchains/caches exist; macOS SDK/linker inventory | Native Intel, Linux or Windows execution; historical minimum-macOS support; confinement qualification. No builds were attempted by this scout. |
| Linux build machines | Record actual CPU/kernel/glibc/toolchain first; two-path builds and fake smoke; Linux native fixtures on matching CPU with required kernel features | Presence of an aarch64 runner or required kernel rights is not established here. Cross-compiled aarch64 bytes and x86 tests do not qualify arm64. No remote/network probe occurred. |
| Native Intel Mac / Windows x64 runner | Independently required for corresponding packaging, runtime/dependency and provider evidence | Neither arm64 Mac nor Linux results substitute for these runs. |

The dossier's Ubuntu/kernel/glibc and macOS profiles are qualification baselines, not observed build-machine versions or current security recommendations (`docs/dossiers/dctx-plugin-platforms/README.md:30`, `:39`).

## 5. Promotion must fail closed

Implement a local candidate gate **before any real signature request or index promotion**, distinct from building inspectable artifacts. Predicate:
`promotable = known_exact_target && verified_release_inventory && reproducibility_evidence && accepted_crypto_evidence && native_profile_evidence && lifecycle_privacy_git_evidence && approved_trust && !TEST`.
Missing/stale/mismatched evidence is false; bind evidence to source/recipe/features/target/OS/provider and completed artifact digests, not a manually set `supported=true`.

- General native launch remains closed for **all five targets**: `NativeProvider::launch` always returns unsupported; Linux primitives are not a launcher (`crates/dctx-plugin-platform/src/admission.rs:89`, `:97`; `crates/dctx-plugin-platform/README.md:3`, `:43`). Thus no current default plugin-enabled release is promotable merely from this plan.
- decision 080 permits only verified containing-distribution bundled Git to report `bundled-git-pending-confinement`. It does not waive consent, selection/broker/audit, Git recipe, image binding or lifecycle evidence, and installed standalone/overrides cannot inherit it (`docs/design/plugin-api/README.md:10`; `crates/dctx-plugin-platform/README.md:47`). A blanket full-confinement requirement would misstate that accepted exception; a blanket bundled exemption would also be wrong.
- For standalone plugins require a qualified provider before enablement/handshake. For bundled pending-confinement promotion require the exact decision 080 disposition plus remaining positive/negative native evidence; do not advertise isolation. Unsupported target triples/libc/CPU/minimum-OS combinations remain blocked regardless of successful cross-build.
- Require strict verifier vectors/differential checks and hash evidence; any unresolved mismatch blocks signing/promotion (`crates/dctx-ed25519/README.md:101`; `docs/design/PLUGINS.md:332`). Local fake smoke supplies no platform qualification token.
- Gate fixtures must include all current target refusals, unknown triples, stale/wrong artifact evidence, TEST trust, forged bundled provenance, and a fully qualified synthetic positive control that can never be published. Packaging may emit clearly marked unqualified local candidates; discovery/public promotion consumes only gate-accepted bytes.
