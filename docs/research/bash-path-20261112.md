# Shell-path output size versus MCP defaults, 2026-11-12

## Verdict

**Hypothesis not supported on the required fixture.** CLI defaults did not
produce larger pages than MCP-equivalent bounds for these queries. None of the
120 non-export calls in either mode exceeded 30,000 stdout bytes; their largest
answer was 824 bytes. Export produced 1,002,257 bytes on every call in both modes.
That shared unbounded operation is a shell truncation risk, but does not show a
CLI-versus-MCP default-size difference. Consequently this change adds no
"Agents using a shell" subsection to MODALITIES and changes no CLI defaults.

The supplied external Windows comparison used a different 1,551-file repository,
20 questions and 180 tool calls per arm:

| Arm | Session tokens | Score / 20 |
| --- | ---: | ---: |
| grep-only | 1.87 M | 19.7 |
| dctx MCP | 2.39 M | 19.7 |
| dctx through a shell | 3.32 M | 16.3 |

Those aggregates establish a worse shell result, but do not establish its cause.
No individual queries, client truncation notices or retry traces were supplied.
The proposed chain is plausible: larger answers can be cut by a shell tool,
missing evidence can hurt answers, and re-querying can spend more session tokens.
It was not reproduced here. Equal total call counts also do not establish
whether retries displaced other useful calls. Tool selection, explicit JSON,
root scope and repeated conversation context remain unmeasured alternatives.

The earlier [MCP cost study](mcp-cost-20261112.md) did exercise a larger impact
answer: CLI defaults produced 42,994 text bytes, while MCP-equivalent bounds
produced 6,339. That demonstrates a possible size mechanism on another corpus;
it does not prove why the external tester's shell arm lost accuracy or tokens.
With matching options, MCP content equals CLI stdout byte for byte. Transport
alone does not make the engine return less evidence.

## Method

Measured the release CLI built offline from revision `cfff834ee380` on Linux.
[shell_output_size.py](../../tools/bench/shell_output_size.py) imports
`generate_fixture` from [map_find_latency.py](../../tools/bench/map_find_latency.py)
and calls it with `scale_files=1551`. It does not copy or augment the generator.
The fixture has 1,551 files, 106 directories including its root, and four directory
levels: 388 Rust, 388 Python, 388 Markdown and 387 JSON files. Sources have settled
mtimes; there are no sleeps or timing assertions.

The fixed, ordered terms are actual Rust/Python symbol names:

```text
latency_probe
helper
scale_item_000001
scale_item_000004
scale_item_000005
scale_item_000100
scale_item_000401
scale_item_001000
scale_item_001548
scale_item_001549
```

All thirteen tools exposed by the default MCP server have CLI equivalents in the
measurement. Each runs once per term per mode: **13 × 10 × 2 = 260 calls**.
The modes use CLI defaults or add exactly the MCP-specific default overrides
listed below. Both modes omit optional JSON, except export, which uses the
explicit `--format json` required by the MCP schema.

- Find and grep use the literal term; task pack uses the backtick-quoted name.
- Map and skeleton use the term's containing file. Neighbors, explain, read and
  impact use its stable symbol ID. Read measures ordinary source reads; optional
  `context:true`, custom filters, pagination and other encodings are outside this run.
- Path and trace pair the symbol with `latency_probe`; `latency_probe` itself
  is paired with `helper`. This includes the fixture's sole call edge and no-path
  cases. Independent generated functions have no callers.
- Hubs and export have no term argument; their identical requests are repeated
  ten times per mode and are not ten distinct queries.

Every process runs in the same generated root with isolated configuration and
a shared worktree-local index cache. Inherited `DCTX_*` overrides are removed.
Complete stdout is captured by Python `subprocess`, with no client truncator.
Each JSON sample records command, mode, term, relative argument vector, raw byte
count including final LF, line count including any unterminated last line, and
whether bytes are strictly greater than 30,000. No binary or temporary host paths
are written to the JSON. Failures remove stale reports and propagate a nonzero exit.

The 30,000-byte threshold is a screening proxy for the supplied approximately
30,000-character Bash-tool limit, not a measured client limit or a universal
byte/character equivalence. This experiment does not run that client, measure
model tokens, answers or retries, or compare MCP wire envelopes. Arithmetic
medians retain half-byte values; p95 uses nearest rank (the maximum for ten
samples). The JSON also contains all raw samples and 26 summary rows.

## Matching MCP bounds from a shell

These are the exact differing defaults, from the MCP default mapping and CLI
option defaults. They are useful for controlled comparisons even though the
fixture did not reach the limits.

| Operation | CLI default | Flags matching MCP defaults |
| --- | --- | --- |
| map | 60 records | `--limit 20` |
| hubs | 20 records | `--limit 10` |
| trace | 10 paths, 65,536 bytes | `--max-paths 5 --max-bytes 8192` |
| impact | 1,000 sites, 65,536 bytes | `--max-sites 50 --max-bytes 8192` |
| task pack | 3,000 estimated tokens | `--budget 2000` |

From the same scoped root as the MCP server, this is a bounded shell recipe
using text output. Set `query` to the name being investigated, `file` to its
relative source path, and `id` / `to` to exact symbol IDs returned by find.

```sh
dctx map find --budget 500 --limit 10 -- "$query"
dctx map map --budget 500 --limit 20 -- "$file"
dctx map neighbors --budget 500 --limit 20 -- "$id"
dctx map explain --budget 500 -- "$id"
dctx map read --budget 2000 -- "$id"
dctx map skeleton --budget 2000 -- "$file"
dctx map grep --budget 500 --limit 10 -- "$query"
dctx map hubs --budget 2000 --limit 10
dctx map path --budget 2000 -- "$id" "$to"
dctx trace --max-depth 8 --max-paths 5 --max-bytes 8192 -- "$id" "$to"
dctx impact --max-depth 8 --max-sites 50 --max-bytes 8192 -- "$id"
dctx pack --budget 2000 --for "$query"
```

The explicit shared budgets in this recipe reproduce the ordinary MCP defaults;
the script leaves shared defaults implicit. Match any additional MCP parameters
too, including `json:true` with `--json`, direction, filters and cursors. Read's
optional `context:true` instead maps to `dctx context` with a 3,000-token default.
Use the returned opaque `next` with `--cursor` on the same paginated query when
more evidence is needed. Engine bounds report partial results; they do not
guarantee that the first page answers the question. Export has no bounded MCP
equivalent: save it to a file with `dctx map export --format json --output graph.json`
and inspect selected portions instead of printing the graph into a shell tool.

## Reproduction and validation

Use an offline-populated Cargo registry in the worktree-local `CARGO_HOME` below.
The build uses the lockfile and default features:

```sh
umask 022
export CARGO_HOME="$PWD/target/D1112-BASHPATH/cargo-home"
export CARGO_TARGET_DIR="$PWD/target/D1112-BASHPATH/build"
export XDG_CACHE_HOME="$PWD/target/D1112-BASHPATH/xdg-cache"
export XDG_CONFIG_HOME="$PWD/target/D1112-BASHPATH/config"
export XDG_DATA_HOME="$PWD/target/D1112-BASHPATH/data"
export TMPDIR="$PWD/target/D1112-BASHPATH/tmp"
export PYTHONPYCACHEPREFIX="$PWD/target/D1112-BASHPATH/pycache"
mkdir -p "$CARGO_HOME" "$TMPDIR" "$XDG_CACHE_HOME" "$XDG_CONFIG_HOME" "$XDG_DATA_HOME"
cargo build --offline --locked --release -p dctx-cli
python3 -m unittest discover -s tools/bench/tests
python3 tools/bench/shell_output_size.py \
  --binary target/D1112-BASHPATH/build/release/dctx-cli \
  --output target/D1112-BASHPATH/sizes.json
```

The release build exited 0. The combined check passed: **41 tests, zero failures**
(seven new output-size tests), then **260 measured CLI calls, exit 0**. Tests cover
the fixed real symbol list, every command in both modes and exact MCP overrides,
UTF-8 byte and line accounting, threshold boundaries, JSON shape and serialization,
median/p95/max/count summaries, printed tables, and stale-report removal on errors.
The generated table above matches the local JSON report. All build products,
registry copies, caches and raw JSON remain under ignored `target/D1112-BASHPATH/`.
