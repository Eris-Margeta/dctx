# Shell-path output size, 2026-11-12

## Verdict

CLI defaults produced small pages for the queries on the required fixture.
None of the 120 non-export calls exceeded 30,000 stdout bytes; the largest
answer was 824 bytes. Export produced 1,002,257 bytes on each of ten calls.
That unbounded operation is a shell truncation risk. This fixture does not
establish why a shell agent used more tokens on a different repository.

The supplied external Windows comparison used a different 1,551-file repository,
20 questions and 180 tool calls per arm:

| Arm | Session tokens | Score / 20 |
| --- | ---: | ---: |
| grep-only | 1.87 M | 19.7 |
| dctx through a shell | 3.32 M | 16.3 |

Those aggregates establish a worse shell result, but do not establish its cause.
No individual queries, client truncation notices or retry traces were supplied.
Larger answers can be cut by a shell tool, missing evidence can hurt answers,
and re-querying can spend more session tokens. That sequence was not reproduced
here. Equal total call counts do not establish whether retries displaced other
useful calls. Tool selection, explicit JSON, root scope and repeated conversation
context remain unmeasured alternatives.

The earlier [CLI output study](cli-output-20261112.md) exercised a larger impact
answer: CLI defaults produced 42,994 text bytes, while explicit bounds produced
6,339. That demonstrates a possible size mechanism on another corpus; it does
not prove why the external tester's shell arm lost accuracy or tokens.

## Method

Measured the release CLI built offline from revision `cfff834ee380` on Linux.
The fixture generator from [map_find_latency.py](../../tools/bench/map_find_latency.py)
was called with `scale_files=1551`, without copying or augmenting the generator.
It produced 1,551 files, 106 directories including its root, and four directory
levels: 388 Rust, 388 Python, 388 Markdown and 387 JSON files. Sources had settled
mtimes; no sleeps or timing assertions were used.

The fixed, ordered terms were actual Rust/Python symbol names:

```text
latency_probe
helper
scale_item_000001
scale_item_000004
scale_item_000005
scale_item_000100
scale_item_000401
scale_item_001000
scale_item_001548
scale_item_001549
```

The CLI-default results below cover thirteen commands, once per term:
**13 × 10 = 130 calls**. Commands omitted optional JSON, except export, which
used explicit `--format json`.

- Find and grep used the literal term; task pack used the backtick-quoted name.
- Map and skeleton used the term's containing file. Neighbors, explain, read and
  impact used its stable symbol ID. Read measured ordinary source reads.
- Path and trace paired the symbol with `latency_probe`; `latency_probe` itself
  was paired with `helper`. This included the fixture's sole call edge and
  no-path cases. Independent generated functions had no callers.
- Hubs and export had no term argument; their identical requests were repeated
  ten times and were not ten distinct queries.

Every process ran in the same generated root with isolated configuration and
a shared worktree-local index cache. Inherited `DCTX_*` overrides were removed.
Complete stdout was captured by Python `subprocess`, with no client truncator.
Counts include the final LF. The 30,000-byte threshold is a screening proxy for
the supplied approximately 30,000-character Bash-tool limit, not a measured
client limit or a universal byte/character equivalence. This experiment did not
measure model tokens, answers or retries. Arithmetic medians retain half-byte
values; p95 uses nearest rank (the maximum for ten samples).

The fixture matches the external repository's file count, not its source sizes,
symbol fanout or query distribution. Its tiny bodies and single call edge do not
stress impact site limits or large source pages. A negative result here cannot
rule out truncation on that private repository. Attribution needs the original
arguments, pre/post-truncation output and call traces, followed by a same-client
rerun with matched options.

## Bounding output from a shell

These explicit bounds are useful when investigating output size. The fixture
above did not reach them; its table reports CLI defaults.

| Operation | CLI default | Smaller explicit bound |
| --- | --- | --- |
| map | 60 records | `--limit 20` |
| hubs | 20 records | `--limit 10` |
| trace | 10 paths, 65,536 bytes | `--max-paths 5 --max-bytes 8192` |
| impact | 1,000 sites, 65,536 bytes | `--max-sites 50 --max-bytes 8192` |
| task pack | 3,000 estimated tokens | `--budget 2000` |

Run from a scoped project root. Set `query` to the name being investigated,
`file` to its relative source path, and `id` / `to` to exact symbol IDs returned
by find. This recipe uses text output:

```sh
dctx map find --budget 500 --limit 10 -- "$query"
dctx map map --budget 500 --limit 20 -- "$file"
dctx map neighbors --budget 500 --limit 20 -- "$id"
dctx map explain --budget 500 -- "$id"
dctx map read --budget 2000 -- "$id"
dctx map skeleton --budget 2000 -- "$file"
dctx map grep --budget 500 --limit 10 -- "$query"
dctx map hubs --budget 2000 --limit 10
dctx map path --budget 2000 -- "$id" "$to"
dctx trace --max-depth 8 --max-paths 5 --max-bytes 8192 -- "$id" "$to"
dctx impact --max-depth 8 --max-sites 50 --max-bytes 8192 -- "$id"
dctx pack --budget 2000 --for "$query"
```


Add `--json` when structured output is needed, and keep direction, filters and
cursors consistent across comparisons. Named context uses `dctx context` with
a 3,000-token default. Use the returned opaque `next` with `--cursor` on the
same paginated query when more evidence is needed. Engine bounds report partial
results; they do not guarantee that the first page answers the question.
Save export to a file with `dctx map export --format json --output graph.json`
and inspect selected portions instead of printing the graph into a shell tool.

## Reproduction

Use the [shell output measurement tool](../../tools/bench/shell_output_size.py)
with a release CLI built from the lockfile and a worktree-local target and cache.
The historical table above records the original revision, fixture and queries;
current CLI output can differ as the engine changes. Keep build products,
configuration, caches and raw reports under ignored `target/`.
