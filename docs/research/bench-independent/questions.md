# Independent benchmark: question set and protocol (protocol v1)

Written on 31 October 2026, before the v1.0.0 tag exists, so before anyone knows which repos the seed will pick. Nothing
in this file or in the scripts may change after the tag; a change means a new protocol version with a new seed.

## Why this protocol

The October protocol (70 questions, `../bench-3way-20261030/tasks/`) was designed by the dctx team, its gold came from our
own line scanner (`goldlib.py`), and dctx was tuned against its corpora. This protocol removes those three biases:

| Bias | Removed by |
|---|---|
| We pick the repos | `select.sh`: the sha of the commit tagged v1.0.0 picks one repo per language from the fixed list in `repos.json`, `sha256("<seed>:<lang>") mod n`. Every corpus we ever measured or tuned on is excluded, and an excluded candidate is a hard error. |
| We define the right answer | `gold_lsp.py`: callers, callees and outlines come from the language servers (`rust-analyzer`, `pyright`, `gopls`, pinned), via `callHierarchy/incomingCalls`, `outgoingCalls` and `documentSymbol`. No benchmarked tool runs before the gold is written. |
| We write the questions | `questions.py`: 20 questions generated by fixed rules from that gold and from the repos' own fix history (commit subjects that reference an issue or PR). |
| Tokens counted differently per tool | One tokenizer for all tools: tiktoken 0.8.0 `cl100k_base`, BPE file pinned by sha256, over raw stdout including banners. |

**Deviation from the benchmark brief (§2.6 (c)).** The brief asks for 20 questions written independently by a researcher who has
never seen dctx output. The repos are not known until the v1.0.0 tag exists, so no question can be written today. Instead,
the generator is written now, before the seed. It is the same rule for every repo and cannot be tuned to repos nobody
knows yet. The concept questions are still human-written text: each one is the subject line a maintainer wrote when
fixing an issue.

## The 20 questions

The three selected repos are in selection order (rust, python, go). Repos 1 and 2 get 7 questions, repo 3 gets 6 (no impact
question). Target-based questions draw from the LSP gold targets in a seeded order, one target per question, never reused.

| Kind | Question | Facts (all checked against the repo through the language server or git) |
|---|---|---|
| def | Where is `NAME` defined? | file and start line (±3 lines) |
| callers ×2 | Which functions call `NAME` (defined in FILE)? Give the file and line of each call. | one fact per calling file: the path and one of its call lines, at most 10 files, most calls first |
| callees | Which functions of this repository does `NAME` (FILE) call? | the names of in-repo functions from `outgoingCalls`, at most 10 |
| outline | List the top-level definitions in FILE. | the names of the file's top-level document symbols, at most 12 |
| impact | If `NAME` (FILE) changes, which files are affected through its callers, up to two levels? | the paths of depth-1 and depth-2 calling files, at most 10 |
| concept | Where is the code for: WORDS? | the source files (non-test) changed by the fix commit that still exist at the tag |

**Concept questions.** These come from commits before the pinned tag, merges excluded. The subject must reference `#123` or
`gh-123` and must not start with Merge or Revert. Cleaning removes the reference, a conventional prefix (`fix(cli):`), a
leading fix/close/resolve verb and a trailing "closes". At least 3 words must remain. The commit must change 1 to 3 non-test
source files of the language that still exist at the tag. Candidates are taken in a seeded order.

Targets are functions and methods from non-test files, at least 4 characters long, excluding `main`, `test*` and `__*`.
A target is used only when the language server reports at least one call site.

## Commands per tool (fixed before selection)

Each tool gets its own natural verb. "find" steps only resolve ids and never count for caller facts.

| Kind | dctx | Trail-Code 0.28.0 | graphify 0.9.97 (code-only) |
|---|---|---|---|
| def | `map find NAME --limit 10` | `ask NAME -n 3` | `explain NODE` |
| callers | find, then `map neighbors ID --edge calls --dir in` | `callers NAME` | explain (find), then `affected NODE --relation calls --depth 1` |
| callees | find, then `map neighbors ID --edge calls --dir out` | `callers NAME --direction out` | `explain NODE --all` |
| outline | `map skeleton FILE` | `skeleton FILE` | `explain FILE_NODE --all` |
| impact | find, then neighbors `--dir in --depth 2` | `callers NAME -d 2` | explain (find), then `affected … --depth 2` |
| concept | `map find "WORDS" --limit 10` | `ask "WORDS"` | `query "WORDS" --budget 2000` |

## Scoring

- **Questions.** This is the October rule (`tasks_score.score_question`), unchanged. A fact counts when it appears in the
  question's raw outputs. A question scores 2 points when at least 80 % of its facts are present, 1 point when any fact is
  present, and 0 otherwise. The maximum is 40 points.
- **Callers precision and recall.** The gold is the 20 LSP targets per repo. A tool's caller record is right when its line
  range covers a gold call site. Recall is the share of gold sites that are covered. For dctx the first page counts, and
  the same measure over up to 5 pages is reported next to it. A target whose id the tool cannot resolve counts as all
  sites missed.
- **Precision is a lower bound for every tool.** Language servers miss some dynamic calls, such as Python receivers and Go
  interface dispatch. A real call that the server missed is therefore counted against the tool that found it.

The table is published whatever the numbers are, in `results/<timestamp>/table.md`, with the raw JSONL next to it.
