# MCP transport cost, 2026-11-12

## Scope and method

The supplied private benchmark aggregates are: MCP 15.92 M tokens, 911 s,
239 turns; CLI 14.16 M, 720 s, 130 turns; grep 14.90 M, 701 s, 172 turns.
The Windows comparison is 2.39 M versus 1.87 M tokens at equal accuracy.
No private task data or individual traces were available. These aggregates show
an overhead problem, but cannot attribute turns to particular tool sequences or
prove how much of the session difference this patch removes. MCP has 39% more
turns and 30% more wall time than grep in those aggregates. They do not establish
that an individual MCP dispatch is slower: additional model/tool round trips are
a plausible driver, especially because ordinary MCP and CLI use the same query
implementation. A full session rerun is needed to quantify the actual gain.

The local corpus is the complete tracked repository at `a6259da2`, exported with
`git archive HEAD` into an ignored directory under `target/`. Both executables
query that same frozen corpus, with its ignore rules, isolated configuration,
and a shared worktree-local index cache. Freezing avoids rebuilding the index
while the implementation is being edited. The before executable was built before
this patch; the after executable includes it. No repository files were excluded
beyond the normal indexing policy. Build products, caches and raw local
measurements remain under ignored `target/`.

Measurements count UTF-8 bytes, not tokenizer estimates. “Wire” includes the
entire minified JSON-RPC response and its terminal LF, with request id `1`.
“Text” counts the decoded `result.content[0].text` string. CLI bytes count stdout,
including LF, without a shell wrapper. The tools/list result count excludes the
JSON-RPC envelope, but includes **all** tool descriptions and complete schemas.

All successful MCP content strings equal CLI stdout with matching options byte for byte.
The default find/read/incoming-neighbors replies total 935 bytes in three calls;
the task pack is 1,306 bytes in one call and also includes outgoing relations.
This trades a larger combined answer for fewer model/tool round trips, rather
than claiming a response-byte saving. Explicit JSON for those three primitive
queries totals 2,886 bytes, 3.09 times their text wire size.

The impact default text reply shrinks 85.11%, from 43,534 to 6,481 wire bytes;
its explicit-JSON reply shrinks 87.81%, from 70,772 to 8,625. This is a smaller
bounded answer, with truncation reported, not lossless compression. Explicitly
restoring the old bounds remains supported and is covered by a CLI parity test.

The requests are:

- `find {"query":"estimate_tokens"}`; CLI `map find estimate_tokens`.
- `read {"id":"s:crates/dctx-core/src/budget.rs#estimate_tokens"}`;
  CLI `map read` with that id.
- `neighbors` with the same id, `dir:"in"`, `edge:["calls"]`;
  CLI `map neighbors ID --dir in --edge calls`.
- Named context: the same `read` id with `context:true`; CLI `context ID`.
- ``pack {"task":"`estimate_tokens`"}``;
  CLI ``pack --for '`estimate_tokens`' --budget 2000`` after this patch.
  Before, no pack MCP tool existed; its error is not a successful context answer.
  The before CLI comparison uses its existing 3000-token default.

The impact query uses `symbol:"s:crates/dctx-core/src/budget.rs#estimate_tokens"`.
Its CLI comparison uses the same symbol and, after this patch, explicit
`--max-sites 50 --max-bytes 8192` to match the new MCP defaults; the baseline CLI
uses its existing defaults. No filter or symbol changed between these arms.

JSON rows add `json:true` to the same MCP arguments and `--json` to the CLI.
They measure the existing facade JSON carried inside MCP text content. This
patch preserves that representation for explicit JSON callers; it does not send
a duplicate structuredContent copy.

## What causes the overhead

1. **Catalog cost.** Every tool carries descriptions, object scaffolding and
   repeated common parameters. The default server previously used the longest
   descriptions even though shorter descriptions already existed for restricted
   profiles. Shorter descriptions, omission of obvious property descriptions,
   and one description style remove 1,628 bytes from discovery. Protocol names,
   parameter types, required parameters and `additionalProperties:false` remain.
   Whether a client repeats those tokens each model turn depends on that client;
   multiplying catalog bytes by the private turn count is not a token measurement.

2. **Optional JSON costs extra.** The server already defaulted to text; there was
   no unconditional JSON-output bug to fix. Explicit `json:true` carries field
   names and metadata, then quotes/escapes that JSON inside the mandatory MCP
   text envelope. The table distinguishes that overhead from ordinary text.
   Defaults remain text and are now explicitly advertised as `json:false`.
   Successful ordinary query content remains byte-identical to CLI text.

3. **Bounds existed, but were uneven and poorly advertised.** Find already
   defaulted to 10 records, neighbors to 20, ordinary pages to 500 estimated
   tokens, and source reads to 2000. Cursors already worked; the initial cursor
   should be absent, and the returned opaque `next` value resumes a page.
   Shrinking read pages would risk increasing turns, so their defaults stay.
   Map previously allowed 60 records, hubs 20, while trace/impact allowed 64 KiB
   and impact 1000 sites. MCP now defaults to map 20, hubs 10, trace 5 paths,
   impact 50 sites, and 8192 output bytes for both graph-answer tools. Trace and
   impact retain caller depth 8. Explicit options override defaults, including
   the previous larger values. Existing truncation/continuation reporting stays
   intact. The byte cap applies to the engine page before MCP escaping.

4. **A CLI convenience operation was missing from MCP.** To reproduce task pack
   context using the original tools requires find, neighbors and read calls.
   Each ordinary MCP call opens the existing CLI query path and verifies or
   builds a snapshot; keeping the stdio connection open does not merge those
   transactions. The new `pack` tool calls the existing engine-owned task pack:
   it selects definitions, relations and source against one pinned snapshot.
   This removes the need to assemble that workflow through three primitive calls.
   It does not establish that private benchmark agents actually used that
   sequence. `read context:true` was already another single-call option for a
   named file/symbol; discovery now explicitly explains it.

The new tool is bounded task context, with `task`, optional `budget` (default
2000, range 100..100000), and optional `json`. It does not expose raw filesystem
packing, root-changing or file-output arguments. `--tools pack` selects it;
existing lean/three profile memberships stay unchanged. Pack is a ranked
selection, not an exhaustive list of all callers: use neighbors pagination or
explicitly bounded impact for a complete investigation.

## Reproduction

Build a baseline executable before applying the patch, retain it under `target/`,
and build the patched executable with a separate worktree-local target/cache.
Use the same exported corpus for both. For example, from the repository root:

```sh
umask 022
export CARGO_TARGET_DIR="$PWD/target/mcp-cost-build"
export CARGO_HOME="$PWD/target/mcp-cost-cargo"
export XDG_CACHE_HOME="$PWD/target/mcp-cost-cache"
export XDG_CONFIG_HOME="$PWD/target/mcp-cost-config"
export XDG_DATA_HOME="$PWD/target/mcp-cost-data"
export TMPDIR="$PWD/target/mcp-cost-tmp"
export DCTX_CACHE_DIR="$PWD/target/mcp-cost-index"
export DCTX_AUTO_CLEAN=0
mkdir -p target/mcplean-corpus "$XDG_CONFIG_HOME" "$XDG_DATA_HOME" "$TMPDIR"
# Export once, before editing; do not export different revisions for each arm.
git archive a6259da2 | tar -x -C target/mcplean-corpus
cargo build -p dctx-cli --locked
```

Keep the corpus basename `mcplean-corpus` when reproducing exact counts: ordinary
CLI text headers include that name. Run the executable from the exported corpus.
For discovery, write
`{"jsonrpc":"2.0","id":1,"method":"tools/list"}` plus LF to `dctx-cli mcp`
and count the returned line's bytes. For a query, send for example:

```json
{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"find","arguments":{"query":"estimate_tokens"}}}
```

In Python, `len(raw_reply)` is the wire count,
`len(json.loads(raw_reply)["result"]["content"][0]["text"].encode("utf-8"))`
is the content count, and `len(subprocess.run(..., capture_output=True).stdout)`
is the CLI count. Count the tools/list result with
`len(json.dumps(reply["result"], ensure_ascii=False, separators=(",", ":")).encode("utf-8"))`.
Run each query once with text defaults and once with explicit JSON. A warm cache
changes latency but not these payload sizes. No sleeps or timing thresholds are
used as correctness assertions.

## Regression coverage

`crates/dctx-cli/tests/mcp_costs.rs` uses a fixed Rust corpus with one definition
and 80 callers so page and site limits are exercised without depending on future
repository growth. Six tests assert:

- Full tools/list wire reply <= 6800 bytes, original names preserved, and JSON
  explicitly opt-in in the schemas.
- Default find <= 1900 bytes, read <= 600, neighbors <= 2000, pack <= 7400,
  and impact <= 8700 on that fixture, including the MCP envelope.
- Explicit JSON response budgets and CLI byte parity, continuation to a distinct
  second result, and explicit graph bounds overriding the new defaults.
- A single pack includes the symbol location, callers and source. A flag-shaped
  task stays a literal value.

An additional MCP unit test covers omitted/null defaults, explicit overrides,
and rejection of pack root/output/cursor arguments. Existing transport tests
continue to check profile parity, named-context delivery and CLI/RPC equivalence;
graph MCP parity uses CLI flags matching the new MCP defaults.

Validation commands (desktop packages excluded as requested):

```sh
cargo fmt --all -- --check
cargo clippy --workspace --locked --exclude dctx-desktop --exclude dctx-desktop-api --all-targets -- -D warnings
cargo test --workspace --locked --exclude dctx-desktop --exclude dctx-desktop-api
```

All three commands exited 0. The workspace test run completed with 2,541
passed, zero failed and zero ignored, including six new wire-budget integration
tests and one new MCP defaults/argument unit test. No timing gates or sleeps
were added. The supplied private session benchmark was not rerun; these results
establish payload and contract regressions, not a measured session-token or
wall-time improvement.
