ADR-014: Privacy Guarantees & Ignore Semantics

Status: current — architectural principle retained; historical examples describe their original release.

For shipped behavior and limitations, see the README, testing guide and specification. Earlier “formally proven” wording refers to historical tests; tests and defense layers do not constitute a formal proof of all implementations. Date: 2026-02-02 Approved: 2026-02-02 Implemented: 2026-02-02 (WO-050 through WO-054) Deciders: Operator, AI Assistant Context: Phase 10.6 - Safety-Critical Privacy & Performance Audit

Context and Problem Statement#

Users trust dctx with their entire codebases, including sensitive files like .env, .git/, API keys, credentials, and proprietary source code. Our ignore and omit systems were implemented primarily for output cleanliness and token efficiency, but we have not formally guaranteed that ignored files are NEVER read into memory.

Critical Questions: 1. Are ignored files (.env, credentials) ever read into memory? 2. Does the --debug-ignored flag compromise privacy? 3. What is the semantic difference between IGNORE and OMIT? 4. Can template variables accidentally trigger file reads on ignored files? 5. Do we recurse into ignored folders (performance impact)?

Risk: Without formal privacy guarantees, users cannot trust dctx with sensitive codebases. A single accidental file read could expose credentials, leak proprietary code, or violate security policies.

Decision Drivers#

  • Privacy First: Ignored files must NEVER be read, regardless of flags or configuration
  • Performance: Ignored folders must be skipped entirely (no recursion)
  • Semantic Clarity: IGNORE vs OMIT must have clear, enforced meanings
  • Debug Transparency: Users must be able to verify their ignore rules work correctly
  • Template Safety: Custom templates must not accidentally trigger I/O on ignored files
  • Zero Trust: Assume users handle classified/sensitive information

Considered Options#

Option 1: Status Quo (No Formal Guarantees)#

  • Pro: No code changes required
  • Pro: Current behavior is already safe (but undocumented)
  • Con: No formal verification or tests
  • Con: Users cannot trust the system
  • Con: Template variables could be unsafe in the future
  • Verdict: ❌ Rejected - Privacy must be provable, not assumed

Option 2: Full Privacy Audit + Formal Guarantees (SELECTED)#

  • Pro: Provable privacy through code analysis and tests
  • Pro: Clear semantic distinction between IGNORE and OMIT
  • Pro: Template variable safety system prevents accidental reads
  • Pro: Performance optimizations (skip ignored folders)
  • Pro: Debug mode that doesn't compromise privacy
  • Con: Requires implementation work (2-3 hours)
  • Verdict: ✅ SELECTED - Only acceptable solution for sensitive codebases

Option 3: Encryption-Based Approach#

  • Pro: Could encrypt ignored file contents in memory
  • Con: Massive complexity, performance overhead
  • Con: Doesn't solve the problem (still reading files)
  • Verdict: ❌ Rejected - Overengineered, doesn't address root issue

Decision Outcome#

Chosen Option: Option 2 - Full Privacy Audit + Formal Guarantees

We will implement a three-tier rule system with formal privacy guarantees:

Rule System Definition#

Rule Type Directory Tree Visibility File Content Section Recurse into Folders? Read File into Memory?
IGNORE (default) ❌ Hidden ❌ Hidden ❌ NO (skip entirely) ❌ NEVER
IGNORE (--debug-ignored) ✅ Shown with [IGNORED] marker ❌ Hidden ✅ YES (for diagnostics) ❌ NEVER
OMIT (always) ✅ Shown (normal) ⚠️ [Content omitted by pattern rules] ✅ YES ❌ NEVER

Semantic Definitions#

IGNORE#

Meaning: "This file/folder does not exist for our purposes."

Use Cases: - .git/ - Version control internals - node_modules/, target/, __pycache__/ - Build artifacts - .env, .secrets - Credentials and sensitive configuration - *.log, *.tmp - Temporary files

Behavior: - Default: Not visible in tree, not in content, folder not recursed - Debug Mode: Visible in tree with [IGNORED] marker, folder recursed, but files never read - Configuration: .dctxignore (project) or ~/.config/dctx/ignore (global)

OMIT#

Meaning: "This file exists and is relevant to the project structure, but we don't care about its contents."

Use Cases: - package-lock.json, Cargo.lock - Lockfiles (structure matters, content doesn't) - *.svg - Image files (relevant to project, but binary/verbose) - go.sum, yarn.lock - Dependency checksums

Behavior: - Always visible in directory tree (with metadata) - Content section shows: [Content omitted by pattern rules] - File is listed but never read into memory

Debug Mode (--debug-ignored)#

Purpose: Allow users to verify their ignore rules are working correctly.

Behavior: - Temporarily treats IGNORE rules as OMIT rules for visibility - Shows ignored files/folders in directory tree with [IGNORED] marker - Recurses into ignored folders to show structure - CRITICAL: Files are still NEVER read into memory - Grayed-out metadata: SIZE from stat() only, never from content reading - No LINES count (would require reading file)

SENSITIVE (strict deny, v1)#

Meaning: "This file holds credentials. No dctx command ever reads, hashes, indexes or prints its bytes."

Shapes (final path component, ASCII case-insensitive; the single list is dctx_core::filter::is_secret_shaped_name): - env files: .env, .env.*, *.env, .envrc - keys, certificates and keystores: *.pem, *.key, *.p12, *.pfx, *.jks, *.keystore - SSH private keys: id_rsa, id_dsa, id_ecdsa, id_ed25519, and those names with a _/- suffix without a dot (id_rsa_deploy); id_rsa.pub is not matched - credentials: credentials, credentials.<data>, *.credentials.json, secrets.<data> (data = json, yaml, yml, toml, ini, xml); credentials.py and secrets.rs stay ordinary source - token files: .netrc, _netrc, .npmrc, .pypirc, .pgpass, .htpasswd, .git-credentials

Behavior: - The file stays listed by name (pack tree, map inventory) with its content omitted, and is never read. - Applies whether or not the file is git-tracked, to every surface: pack (all view filters, including --include, --ext, --hidden and --debug-ignored), every dctx map verb (map, find, read, explain, skeleton, grep, neighbors, hubs, path, export; by stable id or by raw path; with or without --in) and the dctx mcp tools, which run the same code path. - Enforced in the map policy (PolicyView::decide), again before any map read (Session::read_verified), in map grep, in the pack scan (dctx-pack snapshot) and in the dctx-map-query source adapter. - No override. v1 has no --allow-sensitive flag, and repository or global rule files cannot re-include these shapes. dctx decides by name only; it does not scan contents, so a secret pasted into an ordinary source file is not detected.

Verification: crates/dctx/tests/map_sensitive_files.rs, the unit tests next to is_secret_shaped_name, PolicyView::decide and the pack scan, and the end-to-end check <repo>/scripts/checks/V1-1.zsh (a git-tracked fixture with one canary per shape, run against every command).

.git (hard guard, v1)#

Any path with a .git segment, at any depth, is excluded by PolicyView::decide before the rule layers are consulted, so !.git/, !.g*/ or !nested/.git/** in .gitignore or .dctxignore cannot re-include it: the map verbs never list or read it, and Session::read_verified refuses it too. pack excludes it as well (dctx-pack snapshot); only --debug-ignored still lists it by name, never reading it. Tests: git_negations_never_list_or_read_git in crates/dctx/tests/git_and_symlink_privacy.rs and in the pack snapshot.

Symlinks (v1)#

dctx::FsSource never follows a symlink: a symlinked final component is refused before the open, and the open itself uses O_NOFOLLOW (raw platform values; crates/dctx has no libc dependency), so a symlink swapped in after the stat is refused by the kernel; the opened handle must be a regular file. A symlinked intermediate directory is refused for listings and reads. Tests: crates/dctx/src/adapters/fs.rs and crates/dctx/tests/git_and_symlink_privacy.rs.

DCTX_INDEX_IGNORED=1#

This environment switch (dctx-cli host::project_rules) makes pack and the map verbs ignore every ignore file (global ignore, .gitignore, nested .gitignore, .dctxignore); omit files and the built-in rules still load. It does not touch the SENSITIVE deny, the .git guard or the symlink rules above: those do not come from rule files. <repo>/scripts/checks/V1-1.zsh reruns its canary checks with the switch set.

Privacy Guarantees (Formal)#

Guarantee 1: Ignored Files Never Enter Read Queue ✅#

Assertion: Files matching ignore rules are excluded at tree construction time (walker.rs:136-146) via should_ignore_item() check. They never appear in the DirContextTreeNode tree, therefore never collected by collect_file_paths(), therefore never read by populate_file_contents_parallel().

Verification: ✅ PROVEN - ✅ Static code analysis completed (WO-052) - ✅ Unit test: test_collect_file_paths_skips_ignored - ignored file never in read queue - ✅ Unit test: test_collect_file_paths_skips_ignored_subtree - entire subtrees skipped - ✅ Privacy guarantee formally proven through test chain

Guarantee 2: Ignored Folders Skip Recursion#

Assertion: When a folder matches ignore rules, walk_recursive() uses continue (walker.rs:146) to skip the item entirely. The function is never called recursively on that folder's children.

Verification: - Performance benchmark: 500MB node_modules/ should take < 100ms to skip - Without ignore: Same folder would take 5-10 seconds to scan - Debug mode exception: Recurses but still never reads files

Guarantee 3: Debug Mode Does Not Compromise Privacy ✅#

Assertion: When --debug-ignored is active, the system recurses into ignored folders and shows them in the tree, but the files are marked with is_ignored: true flag. The populate_file_contents_parallel() function respects this flag and never calls fs::read() on ignored files.

Verification: ✅ PROVEN - ✅ Test: test_ignored_files_shown_with_marker - .env appears in tree with [IGNORED] - ✅ Test: test_ignored_files_never_have_content - no content blocks for ignored files - ✅ Test: test_collect_file_paths_skips_ignored - ignored files never enter read queue - ✅ Privacy preserved even in debug mode (WO-051, WO-052, WO-053)

Guarantee 4: Template Variables Cannot Trigger Unsafe Reads ✅#

Assertion: Template variables are classified by I/O requirement: - Metadata-Only: {{{file_id}}}, {{{file_path}}}, {{{file_size}}}, {{{mod}}} (safe - from stat()) - Content-Requiring: {{{lines}}}, {{{content_preview}}} (unsafe - requires fs::read())

For ignored/omitted files, content-requiring variables are never resolved due to !node.is_ignored guard preventing content block rendering.

Verification: ✅ PROVEN - ✅ Test: test_template_variable_safety_for_ignored_files with 6 comprehensive assertions (WO-054) - ✅ Documentation: Module-level safety documentation in llm_formatter.rs - ✅ Documentation: Template Variable Safety section in DEVELOPER-GUIDE.md - ✅ Multi-layer defense prevents any code path from triggering reads on ignored files

Performance Characteristics#

Ignored Folder Skip (Primary Optimization)#

Scenario: Project with 500MB node_modules/ (50,000 files)

Mode Behavior Time fs::read() Calls
Default Skip entire folder < 100ms 0
Without ignore Scan all 50k files 5-10 sec 50,000
Debug mode Recurse but don't read < 500ms 0

Performance Gain: 50-100x faster for large ignored folders.

Omit Pattern Performance#

Scenario: Lockfiles in monorepo (20 files, 10MB each)

Mode Behavior Time Memory
Include all Read all lockfiles ~200ms 200MB
Omit lockfiles Show in tree, skip content ~10ms 2MB

Performance Gain: 20x faster, 100x less memory.

Consequences#

Positive#

✅ Provable Privacy: Users can verify ignored files are never read ✅ Performance Boost: 50-100x faster for projects with large ignored folders ✅ Semantic Clarity: IGNORE vs OMIT distinction is clear and enforced ✅ Debug Transparency: Users can verify ignore rules without compromising privacy ✅ Template Safety: Custom templates cannot accidentally leak ignored file contents ✅ Trust: Enterprise users can confidently use dctx on classified codebases

Neutral#

⚙️ Implementation Cost: 2-3 hours of development work ⚙️ Test Overhead: 4 new privacy tests, 2 performance benchmarks ⚙️ Documentation: ADR, README security section, developer guide updates

Negative#

❌ API Change: walk_recursive() signature changes (internal API only) ❌ Binary Size: +1-2KB for additional logic (negligible) ❌ Complexity: Template variable classification system adds minor complexity
