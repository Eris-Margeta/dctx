Turn a codebase into focused context for AI assistants. Pack a project, find symbols and read exact source locally. Stable output helps prompt caches reuse context.

Installation#

Download the archive for your OS and architecture from GitHub Releases, verify it against SHA256SUMS, extract it, and put dctx (dctx.exe on Windows) on PATH. Archives cover Linux x64/ARM64, macOS x64/ARM64 and Windows x64. CI covers Linux, macOS and Windows; see the matrix and desktop exclusions.

Coming soon: cargo install dctx-cli and npx dctx. Registry packages are not live yet; use the release archives now.

From source#

Requires Rust 1.91 or newer.

git clone https://github.com/Eris-Margeta/dctx
cd dctx
cargo build --locked --release -p dctx-cli
./target/release/dctx-cli --version
alias dctx="$PWD/target/release/dctx-cli"

Cargo builds dctx-cli (dctx-cli.exe on Windows); release archives supply dctx. For a local source installation, use cargo install --locked --path crates/dctx-cli and alias dctx=dctx-cli. On Windows, invoke the executable directly or create a PowerShell alias.

Quick Start#

In 30 seconds, try a tiny project (POSIX shell; on Windows use Git Bash):

mkdir dctx-demo
cd dctx-demo
printf 'def hello(name):\n    return f"Hello, {name}!"\n' > hello.py
dctx map skeleton hello.py

Output from dctx 1.2.0:

# dctx-demo skeleton
m:hello.py  module  L1-2    hello.py
s:hello.py#hello    fn  L1-2    def hello(name):

For your own project:

dctx pack .                # structured context on stdout
dctx pack . --clipboard    # copy it to the clipboard
dctx map find "SnapshotConfig"
dctx mcp                   # stdio tools for an MCP client

pack writes a file only with --output. Tree timestamps are off by default, so a bare touch does not change its output; --tree-stamps=on includes them. Run dctx without arguments for the interactive terminal menu.

What the output looks like#

These are real runs on the tiny kiosk sample, captured by capture.py from the release binary. Commands run inside a copy named kiosk. For source builds, the executable is dctx-cli (or define a dctx alias).

Find a symbol, then read it#

Pass the exact ID from find to read to get its metadata and verified source bytes:

$ dctx map find greet
# kiosk find
s:src/util.rs#greet fn  L2-4
s:web/app.ts#renderGreeting fn  L10-12

$ dctx map read 's:src/util.rs#greet'
# kiosk read
s:src/util.rs#greet fn  src/util.rs
pub fn greet(name: &str) -> String {
    format!("Hello, {}!", title_case(name))
}

For structured consumption, --json puts the same source bytes in source_utf8 (one JSON line, shown verbatim):

$ dctx map read 's:src/util.rs#greet' --json

Connect an MCP client#

Install the CLI archive first. Replace both absolute paths below with your executable and the project to index (on Windows, use dctx.exe and JSON-escaped paths). An explicit project path avoids relying on the client's working directory. For a source build, point command at target/release/dctx-cli.

Claude Code (.mcp.json at the project root) and Cursor (.cursor/mcp.json) use this JSON:

{
  "mcpServers": {
    "dctx": {
      "type": "stdio",
      "command": "/absolute/path/to/dctx",
      "args": ["mcp", "/absolute/path/to/project"]
    }
  }
}

Codex uses ~/.codex/config.toml (or .codex/config.toml in a trusted project):

[mcp_servers.dctx]
command = "/absolute/path/to/dctx"
args = ["mcp", "/absolute/path/to/project"]

Use as a library#

The public Rust API is the dctx facade, rather than the internal dctx-core crate. It exposes sessions for pack, map, templates and cache, with explicit source, clock, cancellation, selection policy and storage ports. crates.io: publishing soon. Use the current tagged Git dependency:

[dependencies]
dctx = { git = "https://github.com/Eris-Margeta/dctx", tag = "v1.2.0" }

This ten-line example packs an in-memory source with an explicit 8 MiB ephemeral storage ceiling. It runs as a Rust doctest in workspace CI; rustdoc supplies the enclosing main and error return type.

use dctx::{memory::{CancelFlag, FixedClock, MemorySource}, *};
let mut source = MemorySource::new();
source.insert_file("hello.rs", b"pub fn hello() {}\n", 0)?;
let mut session = Session::builder(source).clock(FixedClock(Timestamp(0)))
    .cancellation(std::sync::Arc::new(CancelFlag::new())).ceiling(HostCeiling::base())
    .selection(SelectionPolicy::from_texts(&RuleTexts::default())).grants(HostGrants::PermitAll)
    .storage(StoragePolicy::Ephemeral { max_bytes: 8 * 1024 * 1024 }).place("demo").view("pack").build()?;
let mut output = VecSink::new();
session.pack(&PackRequest::new(), &mut output)?;
println!("{}", std::str::from_utf8(output.as_bytes())?);

The facade discovers no home directory, global config or Git executable and starts no plugin host by default. A filesystem integration must provide its own clock and ignore-rule policy; FsSource does not automatically apply .gitignore. See the library integration notes for the boundary between library and CLI behavior. Python and Node bindings are planned; there is no supported in-process package for either yet.

The core belief: prompt-processing efficiency#

Every token you put in front of a model is paid for three times:

  • Prefill — the model must process every input token before it answers. You pay per token, and you wait for it.
  • Cache misses — providers serve repeated prompt prefixes from a cache for a fraction of the price and latency. One changed byte early in a prompt throws the rest of the cache away.
  • Attention — answers get worse as irrelevant tokens pile up.

dctx exists to send the fewest, most relevant bytes, in an order that stays the same between turns, so prompts are smaller, caches hit, and the model reasons over exact source instead of guesses. That is the whole philosophy, and every feature has to earn its place against it. The specification turns it into five testable constraints — bounded, deterministic, prefix-stable, non-redundant, honest — and eight metrics.

One engine for every way software is built#

You work by… dctx gives you
Hand-coding in an unfamiliar codebase dctx map outlines, symbol search and exact source reads
Copy-paste into a chat assistant dctx pack — the whole project or only what changed, in one structured block
Tab completion and IDE assistants A library facade with millisecond reads for the editor's own context budget
Agents in a terminal Bounded, copyable, deterministic answers: five verbs, one record per line
Fully automated software factories A specification for signed organization policy and receipts; the policy lattice is planned

Zero RAG defects#

Chunk retrieval over embeddings fails in predictable ways: it cuts functions in half, returns different chunks for the same question, serves stale code, leaks ignored files, and hides how much it cost. dctx does not use embeddings. It answers from a lexical graph of syntax-owned spans with explicit confidence, verifies source bytes before emitting them, and reports precision and freshness. The spec names ten defect classes and their intended defenses; its roadmap distinguishes the measured baseline from planned work.

Where it comes from#

dctx started in 2025 as dircontxt, written in pure C (legacy-c/), to solve the context problem while we were still moving to an AI workflow: one command that gave a model the whole project — structured, versioned, with diffs and a strict ignore system — instead of pasting forty files. It was rewritten in Rust in 2026 and grew a privacy-first core, a template system, a plugin host, a desktop app and map mode for agents. The goal has not changed: context, engineered.

Map mode: context for agents#

# Run from this repository's root; map needs a file target.
dctx map map crates/dctx-cli/src/lib.rs --depth 2
dctx map find "SnapshotConfig"
# Use a stable ID returned by map/find for neighbors, explain and read.
dctx map neighbors 's:crates/dctx-cli/src/lib.rs#SnapshotConfig' --edge calls --dir in
dctx map explain 's:crates/dctx-cli/src/lib.rs#SnapshotConfig'
dctx map read 's:crates/dctx-cli/src/lib.rs#SnapshotConfig' --json
  • Source bytes: map read prints metadata and verified source content; --json carries the content in source_utf8 for tools.
  • Bounded: output uses an estimated token budget (up to 2,000; explain up to 1,000), not a model tokenizer guarantee, and never splits a record.
  • Deterministic: the same tree and question give the same bytes, so prompt caches hit.
  • Precision and freshness: use --json for the structured metadata. Structural declarations and conservative call edges do not imply exact semantic resolution.
  • Languages: every supported language is in one of three tiers (full, outline, docs); see Language tiers below or run dctx languages.
  • No Git, no network for map queries: identity comes from dctx's own content digest; map does not need Git history or embeddings.
  • Skeleton and grep: dctx map skeleton <file> prints the declaration signatures of one file, with no bodies, in source order. dctx map grep <literal> is an exhaustive literal search of indexed files, with hits grouped by enclosing symbol; -i makes it ASCII case-insensitive.
  • Hubs: dctx map hubs lists the most-called symbols and the file and symbol counts per directory (--limit 1 to 60, default 20).
  • Path: dctx map path <FROM> <TO> prints the shortest edge path (calls, imports, contains) of at most 8 hops, or no path.
  • Export: dctx map export --format json|mermaid writes the whole graph as one deterministic document. The mermaid form is a flowchart of calls and imports. --output PATH writes a file.
  • Neighbors: --edge calls|imports selects the edge kind, and --depth goes up to 4. Inbound call records carry their call-site lines, at most three per record: \tL6,L7 in text and a sites array in JSON.
  • Find: quote a multi-word concept as one argument; a name that spells the whole phrase ranks just under an exact name. For config keys with no symbol match, find falls back to literal hits, and a SCREAMING_CASE key (HOME, DJANGO_SETTINGS_MODULE) always lists the code that reads it after the best exact symbol.
  • Outline of a file: map map <file> lists exported top-level declarations first, then the rest in source order, with impl blocks, constants and tests last; without --budget its page is 1,000 tokens so --limit 40 is not cut early. Map and find text lines are <id>\t<kind>\tL<start>-<end>, since the id already names the path.
  • MCP: dctx mcp runs a stdio MCP server that exposes the map verbs as tools, including skeleton, path and export.
  • Byte-stable answers: the text header is # <place> <verb>, and JSON leaves out the snapshot digest, generation and age. --meta restores them.
  • Source limit: DCTX_MAX_SOURCE_BYTES sets the total source bytes one scan may read (1 to 17179869184; default 1 GiB).

Details: Map mode guide. The benchmark evidence leads with grep plus file reads; older other-tool results are retained as historical evidence. Planned next — agent hooks, blast radius for a diff, delta answers and prefix-stable context tiers — is specified in docs/SPEC.md.

Language tiers#

dctx languages prints this table (--json for tools, --markdown for this block) from the one registry that also drives dctx --version --verbose; a test fails when the block below differs from it.

  • full: symbols and call edges. Call edges are lexical, not type-resolved: they come from names, scopes and imports, never from a type checker, and ambiguous references are dropped.
  • outline: symbols only; no call edges are promised. Shell function bodies can yield same-file call guesses, but v1 does not promise shell call edges.
  • docs: headed sections.
  • Confidence: guess marks the heuristic outline families, and every record from those files carries confidence guess; structural means a dedicated lexer or deterministic document rules.

Organization control#

The dctx Template System (DTS) defines output templates. The specification proposes extending it to selection, budgets, parsers, cache limits, plugins and privacy through a seven-layer, signed policy lattice — built-in → organization → tenant → machine → user → project → session — where each layer can only narrow the one above it. The lattice and dctx policy explain are planned, not current CLI commands. See Part IV of the spec.

Plugins#

External effects are designed to run through out-of-process plugins with explicit capabilities and consent. The bundled Git plugin implements .gitignore protection and optional staging, but the current product host refuses native plugin launch, including the Git recipe; consent alone does not enable execution. See the Plugins guide.

dctx plugin list
dctx plugin info dctx/git

Security & Privacy#

The filesystem selection boundary excludes ignored file contents, including in debug mode.

Rule file Behaviour
.gitignore, .dctxignore, global ignore Excluded from normal selection; --debug-ignored can show ignored path metadata without reading content

Selection happens before any byte is read, hashed, parsed or cached, and is checked again before output leaves the engine.

On top of the rule files there is a strict built-in deny with no override (no flag, no ! negation, not even DCTX_INDEX_IGNORED=1):

  • Sensitive files are listed by name but never read: .env, .env.*, *.env, .envrc, *.pem, *.key, *.p12, *.pfx, *.jks, *.keystore, SSH private keys (id_rsa, id_dsa, id_ecdsa, id_ed25519), credentials, credentials.json and other data extensions, *.credentials.json, secrets.yaml/.yml/.json/.toml, .npmrc, .netrc, .pypirc, .pgpass, .htpasswd, .git-credentials. The full list is in ADR-014.
  • .git at any depth is never listed or read by the map verbs, and never read by pack, even when a rule says !.git/.
  • Symlinks are never followed: the final component is opened with O_NOFOLLOW, and a symlinked directory is listed by name only, never entered or read through.

dctx decides by file name only; a secret pasted into an ordinary source file is not detected. The shipped pack, dctx map and dctx mcp path is guarded by crates/dctx/tests/map_sensitive_files.rs, crates/dctx/tests/git_and_symlink_privacy.rs, crates/dctx/tests/map_env_files.rs, the unit tests in crates/dctx/src/adapters/fs.rs, crates/dctx/src/domain/policy.rs and crates/dctx-pack/src/snapshot.rs, and an end-to-end check that runs every command against a git-tracked canary fixture (<repo>/scripts/checks/V1-1.zsh).

dctx pack . --debug-ignored  # see ignored paths in the tree without reading them

# .dctxignore

The core pack/map workflows run locally, have no telemetry, call no model and make no network calls: the release check (scripts/release-check.sh) counts AF_INET/AF_INET6 connect/send calls under strace -f for every map verb, pack, cache status and mcp, and fails on any (it reports SKIP where strace cannot run). The current product CLI has no TLS network adapter for plugin discovery or downloads; network-capable distribution and plugin designs are documented separately. See the Plugins guide for current limits and SECURITY.md for private vulnerability reporting.

Measured, in the open#

The baseline is grep plus reading files.

A controlled grep-plus-read benchmark that counts whole agent sessions (start-up context, every call, provider cache hits and accuracy) is being prepared; until it is published, dctx makes no whole-session savings claim.

Historical cold indexing of six benchmark corpora took dctx 0.13–1.20 s on one Linux x86_64 runner. This measures CLI wall time, not agent completion time or session cost.

Choosing how to use dctx covers scoping and MCP startup overhead. Measurement evidence describes what was measured (tool-output bytes and estimated tokens); other-tool protocols are retained only as secondary historical notes.

Older protocols and raw results are linked from the benchmark evidence as secondary historical material. See also the changelog.

Out of scope for v1#

  • Any network or cloud feature.
  • Watch or incremental mode beyond re-indexing.
  • Shell call edges (shell is outline tier: symbols only).
  • Embeddings or semantic search.
  • LSP-grade type resolution: call edges are lexical.
  • A stable plugin ABI or desktop API: neither is stable in v1.
  • Cross-repository queries.

CLI Reference#

Usage: dctx <COMMAND> [OPTIONS]
       dctx pack [PATH] [--output PATH] [--clipboard] [--json] [--tree-stamps=on|off]
       dctx pack [PATH] --for <TEXT> [--budget TOKENS]
       dctx map <map|find|neighbors|explain|read|skeleton|grep|hubs|path|export> [--json]
       dctx mcp [PATH]
       dctx cache status|gc|purge|config|auto
       dctx template build <PATH> | template list
       dctx plugin search|install|list|info|enable|disable|remove|update|verify
       dctx git <status|protect>

Pack options:
  -c, --clipboard       Copy to clipboard
  -o, --output <path>   Write the page to one file
  --json                Summary report instead of the source page
  --tree-stamps=on|off  MOD: and SIZE: on tree lines (default off; on = the 1.0.0 text)

Filter options:
  --ext <list>          Only these extensions, e.g. rs,toml
  --binary              Include binary files (excluded by default)
  --empty | --non-empty Only empty / non-empty files
  --large <MB> | --small <MB>
  --hidden              Only hidden files and folders
  --debug-ignored       Show ignored paths without reading them

Run dctx --help for the complete reference and dctx --version --verbose for feature and precision limits.

Use as a library#

[dependencies]
dctx = { path = "crates/dctx" }

This path dependency assumes your Cargo project is at this repository's root; adjust it for another location. crates/dctx is the facade used by the CLI; the desktop uses crates/dctx-desktop-api on top of it. Python, Node and C bindings are planned on the same facade.

Architecture#

dctx/
├── crates/        # Rust workspace: pure core, mode engines, adapters, lexers, plugin host, facade, CLI
├── plugins/       # First-party plugins (dctx-plugin-git)
├── apps/          # dctx-desktop
├── legacy-c/      # The original C implementation (dircontxt)
├── docs/          # Specification, design records, contracts, formal models, guides
├── tools/         # Benchmarks, plugin tooling, test scripts
└── website/       # project website

Start with docs/SPEC.md, then docs/CRATE-MAP.md.
