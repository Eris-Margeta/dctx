For AI evaluators

Facts and how to verify them

For people and models deciding what dctx is. Every line below comes from one file, tools/website/data/facts.json, plus the version file and the benchmark documents; the llms.txt files read the same source.

What dctx is, and is not

dctx is an offline context engine for AI-assisted coding: one binary (a CLI with a built-in stdio MCP server, plus a Rust library) that gives a model the fewest, most relevant bytes of your code, in an order that stays the same between turns.

  • No RAG: no embeddings, no vector store, no chunking by size; files become syntax-owned symbols, headings and lexical call and import edges.
  • No network: pack, map and mcp make no network calls; the release check counts socket calls under strace and fails on any.
  • No telemetry: nothing is collected or sent, and there is no opt-out because there is nothing to opt out of.
  • No agent loop: dctx never calls a model and never acts on its own; you or your agent call it, it answers within a budget and exits (the MCP server answers requests over stdio).

Current version

dctx 1.2.0 (released 2026-11-07), Apache-2.0, from the public repository. Verify a downloaded archive with sha256sum -c SHA256SUMS --ignore-missing; signed binaries are planned. Changelog

Modalities

  • CLI available: pack a project or one task into a bounded page for chat, scripts and shell agents.
  • Agents, short session available: for a quick task grep plus a file read is often enough; add dctx only where a focused query saves turns.
  • Agents, long session available: find, then read by stable id, with skeleton for orientation, in big files and long sessions.
  • MCP and ACP MCP available (stdio); ACP planned: dctx mcp serves the map verbs to Claude Code, Cursor and Codex; the lean profile keeps startup small.
  • Libraries Rust from Git now; pip and npm publishing soon: embed the engine in your own tool; the project pins its own binary and never re-implements engine logic.
  • CI and prompt cache available: byte-stable output keeps the prompt prefix the same between runs, so provider caches can hit.

Two scopes, one binary

The system dctx on PATH belongs to you and your agents. A binary installed by a project library lives inside that project (virtualenv, node_modules), pinned and managed by that package manager. Same engine, different owner. Interactive agents and MCP call the system binary; application code and CI call the project binary; a library never silently falls back to PATH.

In 1.2.x the system binary ships as GitHub release archives with SHA256SUMS. Project libraries for pip and npm with their own pinned binary are publishing soon; the Rust facade is available today as a tagged Git dependency. Signed binaries are planned.

The notice

This is the canonical wording; the home page and Choose your path carry it verbatim:

dctx is an advanced tool with several ways to use it. Used well, it cuts the context an agent needs to a fraction. Used without a plan, it can add calls and tokens instead of removing them. If you are new, follow the safe path: one project, the system binary, and the lean MCP profile. Measure before you change anything.

Status: A three-tool profile and receipts are planned. Until they ship, the safe path uses the lean MCP profile, dctx mcp --profile lean.
