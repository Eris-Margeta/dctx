Give AI the right code, not all of it.

dctx reads your project on your machine and hands an AI only the parts that matter, as one short page. Same project, same page, every time. No network, no telemetry.

Under ~200 files, use grep. dctx pays off on large repos, multi-hop questions and many agents sharing one index.

Four ways to use it

  1. One command turns a folder into one page you can paste into any AI chat. Secret files such as .env are listed by name and never read. Pack a project

  2. Name the task in a few words and set a size limit. dctx picks the matching code, what calls it and its source, and stops at the limit. Pack for a task

  3. The agent searches by name, gets short stable ids back, then reads only the piece it asks for. Same question, same answer, every turn. Map mode guide

  4. Ask for --json and get structured records with the exact source. The Rust library works from Git today; Node is on npm as @tejl/dctx from 1.3.1; use CI artifacts for Python and Go. Embed the library

Project status · in development since January 2026

Not yet stable. Working toward 2.0.

dctx is not yet stable and not enterprise-ready. Until version 2.0, expect breaking changes often.

  1. January 2026First commit 8 January 2026
  2. 1.3.1 · today10 months in development at the 1.3.1 release; not yet stable
  3. denoisingBreaking changes are expected often until 2.0
  4. 2.0 · stableStability is the goal of version 2.0, and the project is working toward it.

Why: AI providers keep changing how they optimize context on their side. dctx adapts to those changes quickly, but not in real time. Stability arrives with 2.0, and the project is working toward it.

Where it comes from: dctx began as an internal tool that was never meant to be open-sourced, so parts of it are still messy. It was opened up because colleagues who rely on it needed it in the open, and development continues in public.

We see an ultimate solution to this problem, and we are denoising it.

Choose your path

dctx fits into your work in a few different ways. Pick the situation that sounds most like yours: each path says what you get, what to set up, the first command to run and the one mistake to avoid.

  • One giant folder

    Who it’s for
    You work inside one very large tree, for example a 200 GB monorepo, data or document folder.
    What you get
    Short answers about only the part of the tree you name; the rest is never scanned.
    What you use
    System binary, scoped roots, ignore rules at each root you query.
    Setup, first command and the pitfall

    Setup

    1. Install the system binary from GitHub Releases and verify it against SHA256SUMS.
    2. Write a .dctxignore at each root you will query: data, generated output and archives out (.gitignore is read too).
    3. Decide which sub-roots a task can name: a package, a service, a document set.
    4. Optional: set fail-fast ceilings with DCTX_MAX_SOURCE_BYTES, DCTX_MAX_RECORDS and DCTX_MAX_ENTRIES.

    First command

    $ dctx map find Config --place packages/service-a --budget 500 --limit 5

    Watch out for

    Pointing an agent at the whole root. Every call then has to scan or index far more than the task needs, and the cache cap can refuse it. Name the sub-root in the task, with --place or by starting in that folder.

    Open the full path

  • Many smaller projects

    Who it’s for
    You move between many small and medium repositories during the day.
    What you get
    Install once, then run find and read from each project directory.
    What you use
    System binary, called directly from a shell or an agent's shell tool.
    Setup, first command and the pitfall

    Setup

    1. Install the system binary once and put it on PATH.
    2. Run the dctx CLI directly from your agent's shell tool.
    3. Start in the project directory, or use --place to name the project root.
    4. Nothing else per project: dctx reads .gitignore and .dctxignore where they already are.

    First command

    $ dctx map find NAME

    Watch out for

    Stale caches of projects you deleted or no longer use. Auto-clean runs once a day and drops unpinned roots after 30 idle days; to clean by hand, run dctx cache status, then dctx cache gc --dry-run or dctx cache purge --root PATH --dry-run.

    Open the full path

  • Agent builder embedding a library

    Who it’s for
    You build an agent, editor or tool and want dctx inside it.
    What you get
    Stable ids and the exact source bytes inside your own app, from the same engine as the CLI.
    What you use
    Project library with its own pinned binary. Install the Node wrapper with npm install @tejl/dctx; use CI artifacts for Python and Go, embed the Rust facade from a tagged Git dependency, or run a pinned CLI binary and read its --json output.
    Setup, first command and the pitfall

    Setup

    1. Pin one version in your project, for example the Rust facade: dctx = { git = "https://github.com/Eris-Margeta/dctx", tag = "v1.3.1" }.
    2. Pass your own ignore rules: the library does not load .gitignore by itself; the host supplies selection policy, storage limits and the clock.
    3. Move ids, not text: call find, keep the returned ids, call read with them.

    First command

    $ cargo test --locked -p dctx-library-example --doc

    Watch out for

    Re-implementing engine logic: parsing or slicing pack text, recounting budgets, rebuilding ids. Treat answers as opaque pages and stable ids; if you need a different shape, ask the engine for --json.

    Open the full path

  • Team or organisation admin

    Who it’s for
    You roll dctx out to a team or a fleet of machines.
    What you get
    One verified, pinned version on every machine, with the same safety rules everywhere.
    What you use
    System binary distributed through your own package channel, one pinned version everywhere.
    Setup, first command and the pitfall

    Setup

    1. Download the release archives from GitHub Releases and verify them against SHA256SUMS and their cosign signatures; each release also ships an SBOM.
    2. Ship one pinned version through your own package manager, image or configuration tool.
    3. Ship shared ignore rules (.dctxignore and a global ignore); the built-in deny for secrets, .git and symlinks always applies.
    4. Tighten the cache cap per machine if you need to: dctx cache config --max-bytes N can only lower it.

    First command

    $ dctx --version

    Watch out for

    Mixing project and system versions without checking. Run dctx doctor to list every binary in reach, and check dctx --version on PATH and the version each project pins, as part of onboarding.

    Open the full path

Not sure? Take the safe path

dctx is an advanced tool with several ways to use it. Used well, it cuts irrelevant text from selected tool answers. It does not save tokens by default; savings depend on a system reusing byte-identical, prefix-stable context. Extra calls can add tokens. If you are new, follow the safe path: one project, the system binary, direct CLI commands. Measure before you change anything.

Status: Receipts are planned. The safe path uses CLI commands from a shell or an agent's shell tool.

The baseline is grep plus reading files. The measured whole-session benchmark found a -5.01 % change in median total tokens with warm dctx CLI; the 25 % savings rule was not met. On this corpus and model dctx did not save 25 % tokens. The claim is accuracy and bounded context: CLI named more required files at about equal or higher token cost. dctx on its own does not save tokens by default. Savings come from a harness or agent system that reuses byte-identical, prefix-stable context across long sessions over a large body of work, with complete control over every byte. No measured savings figure exists for such a system yet. See the caching philosophy and both recall metrics, median and spread, and limitations.

Returned bytes do not measure whole-session cost or establish an advantage over grep plus narrow line-range reads. Choose a mode and count startup context, all model turns and cached input. Evidence and secondary historical tables

Philosophy

The binary is everything. One file holds the engine and the CLI; there is no service to run, no account and no model behind it. It works offline and makes zero network calls. The same tree and the same question give the same bytes, so answers can be compared, cached and trusted. Why dctx exists, in plain words.

Ignored means never read

  • Ignore rules first. .gitignore, .dctxignore and a global ignore exclude files before they are opened. README
  • A built-in deny with no override. Env files, private keys, credential and secret files are listed by name but never read. README
  • .git is closed. Never listed or read by the map verbs, never read by pack. README
  • No symlink escapes. Files open with O_NOFOLLOW; symlinked directories are never entered. README
  • Local only. No telemetry, no model calls, no network for pack and map. README

dctx decides by file name: a secret pasted into an ordinary source file is not detected. README

Install

Two scopes of the same binary: yours on PATH, and one pinned inside a project.

System binary available now

Download the archive for your OS from GitHub Releases, verify it against SHA256SUMS, extract it and put dctx on PATH. Archives cover Linux x64/ARM64, macOS x64/ARM64 and Windows x64. GitHub Releases (v1.3.1) README

Quick start (README)
$ mkdir dctx-demo
$ cd dctx-demo
$ printf 'def hello(name):\n    return f"Hello, {name}!"\n' > hello.py
$ dctx map skeleton hello.py
From source (Rust 1.91 or newer)
$ git clone https://github.com/Eris-Margeta/dctx
$ cd dctx
$ cargo build --locked --release -p dctx-cli
$ ./target/release/dctx-cli --version
$ alias dctx="$PWD/target/release/dctx-cli"

Project libraries Node on npm; Python and Go in CI

Install the Node wrapper with npm install @tejl/dctx, then run npx @tejl/dctx. It pins the matching @tejl/dctx-<platform> optional dependency. Use CI artifacts for Python and Go, or embed the Rust facade from a tagged Git dependency.

Cargo.toml (Rust facade, from Git today)
[dependencies]
dctx = { git = "https://github.com/Eris-Margeta/dctx", tag = "v1.3.1" }

Two scopes, one binary

  • System binary: the dctx on PATH belongs to you and your agents, and you upgrade it. Interactive agents call this one.
  • Project binary (Node from npm; Python and Go from CI): a binary installed by a project library lives inside that project (virtualenv, node_modules), pinned and managed by that package manager. Application code and CI call this one; a library never silently falls back to PATH.
  • Same engine, different owner. dctx doctor lists every binary in reach; verify each against SHA256SUMS and its cosign signature.
