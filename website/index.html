Advanced tool, several ways to use it

dctx is an advanced tool with several ways to use it. Used well, it cuts the context an agent needs to a fraction. Used without a plan, it can add calls and tokens instead of removing them. If you are new, follow the safe path: one project, the system binary, the lean MCP profile. Measure before you change anything.

Status: A three-tool profile and receipts are planned. Until they ship, the safe path uses the lean MCP profile, dctx mcp --profile lean.

Choose your path. Each one has its own setup, first command and pitfall:

  • One giant folder

    You work inside one very large tree, for example a 200 GB monorepo, data or document folder.

    System binary, scoped roots, ignore rules at each root you query.

    Pitfall: Pointing an agent at the whole root.

  • Many smaller projects

    You move between many small and medium repositories during the day.

    System binary, the lean MCP profile once in your agent, nothing per project.

    Pitfall: Stale caches of projects you deleted or no longer use.

  • Agent builder embedding a library

    You build an agent, editor or tool and want dctx inside it.

    Project library with its own pinned binary. pip and npm packages are publishing soon; today use the Rust facade from a tagged Git dependency, or run a pinned CLI binary and read its --json output.

    Pitfall: Re-implementing engine logic: parsing or slicing pack text, recounting budgets, rebuilding ids.

  • Team or organisation admin

    You roll dctx out to a team or a fleet of machines.

    System binary distributed through your own package channel, one pinned version everywhere.

    Pitfall: Mixing project and system versions without checking.

Find a symbol, then read it#

Pass the exact ID from find to read to get its metadata and verified source bytes:

$ dctx map find greet
# kiosk find
s:src/util.rs#greet fn  L2-4
s:web/app.ts#renderGreeting fn  L10-12

$ dctx map read 's:src/util.rs#greet'
# kiosk read
s:src/util.rs#greet fn  src/util.rs
pub fn greet(name: &str) -> String {
    format!("Hello, {}!", title_case(name))
}

Ways to use it

One binary, several modalities. Each has its own setup, cost and limits.

  • CLI

    Pack a project or one task into a bounded page for chat, scripts and shell agents.

    available

  • Agents, short session

    For a quick task grep plus a file read is often enough; add dctx only where a focused query saves turns.

    available

  • Agents, long session

    Find, then read by stable id, with skeleton for orientation, in big files and long sessions.

    available

  • MCP and ACP

    dctx mcp serves the map verbs to Claude Code, Cursor and Codex; the lean profile keeps startup small.

    MCP available (stdio); ACP planned

  • Libraries

    Embed the engine in your own tool; the project pins its own binary and never re-implements engine logic.

    Rust from Git now; pip and npm publishing soon

  • CI and prompt cache

    Byte-stable output keeps the prompt prefix the same between runs, so provider caches can hit.

    available

Philosophy

The binary is everything. One file holds the engine, the CLI and the MCP server; there is no service to run, no account and no model behind it. It works offline and makes zero network calls. The same tree and the same question give the same bytes, so answers can be compared, cached and trusted. Why dctx exists, in plain words.

Ignored means never read

  • Ignore rules first. .gitignore, .dctxignore and a global ignore exclude files before they are opened. README
  • A built-in deny with no override. Env files, private keys, credential and secret files are listed by name but never read. README
  • .git is closed. Never listed or read by the map verbs, never read by pack. README
  • No symlink escapes. Files open with O_NOFOLLOW; symlinked directories are never entered. README
  • Local only. No telemetry, no model calls, no network for pack and map. README

dctx decides by file name: a secret pasted into an ordinary source file is not detected. README

Install

Two scopes of the same binary: yours on PATH, and one pinned inside a project.

System binary available now

Download the archive for your OS from GitHub Releases, verify it against SHA256SUMS, extract it and put dctx on PATH. Archives cover Linux x64/ARM64, macOS x64/ARM64 and Windows x64. GitHub Releases (v1.2.0) README

Quick start (README)
$ mkdir dctx-demo
$ cd dctx-demo
$ printf 'def hello(name):\n    return f"Hello, {name}!"\n' > hello.py
$ dctx map skeleton hello.py
From source (Rust 1.91 or newer)
$ git clone https://github.com/Eris-Margeta/dctx
$ cd dctx
$ cargo build --locked --release -p dctx-cli
$ ./target/release/dctx-cli --version
$ alias dctx="$PWD/target/release/dctx-cli"

Project libraries publishing soon

pip and npm packages that carry their own pinned binary are publishing soon, as are cargo install dctx-cli and npx dctx. Today, embed the Rust facade from a tagged Git dependency.

Cargo.toml (Rust facade, from Git today)
[dependencies]
dctx = { git = "https://github.com/Eris-Margeta/dctx", tag = "v1.2.0" }

Two scopes, one binary

  • System binary: the dctx on PATH belongs to you and your agents, and you upgrade it. Interactive agents and MCP call this one.
  • Project binary (planned with the Python and Node libraries): a binary installed by a project library lives inside that project (virtualenv, node_modules), pinned and managed by that package manager. Application code and CI call this one; a library never silently falls back to PATH.
  • Same engine, different owner. Release signing is planned; today both are verified against SHA256SUMS.
