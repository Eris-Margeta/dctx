Our core belief

Prompt‑processing efficiency is the product.

Every token in front of a model is paid for three times — in prefill, in cache misses and in attention. dctx is engineered to cut all three.

Prefill

A model must process every input token before it answers — you pay for each one and wait for it. dctx answers with exact spans and diffs instead of whole files, inside a hard budget.

Cache hits

Providers serve repeated prompt prefixes at a fraction of the price and latency, but one changed byte breaks the cache. dctx output is deterministic and canonically ordered — no timestamps, no random ids.

Attention

Answers get worse as irrelevant tokens pile up. dctx ranks and bounds every answer and labels it with its precision and freshness, so a model reasons over facts, not guesses.

Accuracy

Zero RAG defects, by construction.

Retrieval over embedded chunks fails in predictable ways. dctx does not use embeddings: it answers from a lexical graph of syntax-owned spans and verifies bytes before it emits them.

Security & privacy

Built for codebases you cannot afford to leak.

Ignored means never read

Files excluded by .gitignore, .dctxignore or policy are classified before a single byte is opened, hashed or cached — enforced by read-spy tests.

No network, no VCS in the core

The core never opens a socket, never runs git and never reads .git/. Identity comes from dctx's own content digest.

Signed, sandboxed plugins

Anything with an outside effect is an opt-in plugin: out of process, consent-gated, receipted and signature-verified with vetted Ed25519 cryptography.

Organization control

One signed policy, from the board to the terminal.

The same language that defines dctx output templates controls selection, budgets, parsers, cache limits, plugins and privacy for every mode. Seven layers; each can only narrow the one above it.

  • Narrowing only. A team or developer that tries to widen a company rule gets a precise error, never a silent override.
  • Signed bundles. Distribute one verified policy file through your device management to every machine.
  • Explainable. dctx policy explain shows every effective value and the layer that set it.

Roadmap Template-based policy is available today; the seven-layer signed lattice is specified and in development.

Questions

Answers for decision makers.

Does any of our source code leave our network?

No. dctx runs entirely on your machines. It has no telemetry, makes no network requests and never calls a model. What reaches a model is exactly what your developers or agents choose to send, already bounded by your policy.

How is dctx different from retrieval-augmented generation?

dctx does not use embeddings or vector search. It builds a lexical graph of your code from syntax, answers with whole, byte-verified spans in a deterministic order, and labels every answer with its precision and freshness. That removes the typical failure modes of chunk retrieval and keeps prompts cache-friendly.

Which languages does it understand?

Fifteen language families today: Rust, JavaScript, TypeScript and TSX, Python, Go, Java, C and C++, C#, Kotlin, Ruby, PHP, Swift, Markdown, and JSON, TOML and YAML configuration. Unsupported files are listed honestly, never guessed at.

Does it work with the AI tools our teams already use?

Yes. dctx works through the shell that every coding agent already has, through the clipboard for chat assistants, and as a library. A native tool-protocol server and agent hooks are specified on the roadmap.

What is the difference between open source and Enterprise?

The open repository is Apache-2.0 and ongoing work; parts of it still use third-party dependencies, which we do not consider enterprise-ready.
