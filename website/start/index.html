Start

Choose your path

dctx is one binary used in very different ways. Each way has its own setup, its own first command and its own way to go wrong. Pick the one closest to your work.

Advanced tool, several ways to use it

dctx is an advanced tool with several ways to use it. Used well, it cuts the context an agent needs to a fraction. Used without a plan, it can add calls and tokens instead of removing them. If you are new, follow the safe path: one project, the system binary, the lean MCP profile. Measure before you change anything.

Status: Receipts are planned. The safe path uses the lean MCP profile, dctx mcp --profile lean.

Four paths

  • One giant folder

    You work inside one very large tree, for example a 200 GB monorepo, data or document folder.

    System binary, scoped roots, ignore rules at each root you query.

    Pitfall: Pointing an agent at the whole root.

  • Many smaller projects

    You move between many small and medium repositories during the day.

    System binary, the lean MCP profile once in your agent, nothing per project.

    Pitfall: Stale caches of projects you deleted or no longer use.

  • Agent builder embedding a library

    You build an agent, editor or tool and want dctx inside it.

    Project library with its own pinned binary. The Python, Node and Go wrappers over dctx rpc are built and tested in CI, with registry publication pending; today use the Rust facade from a tagged Git dependency, or run a pinned CLI binary and read its --json output.

    Pitfall: Re-implementing engine logic: parsing or slicing pack text, recounting budgets, rebuilding ids.

  • Team or organisation admin

    You roll dctx out to a team or a fleet of machines.

    System binary distributed through your own package channel, one pinned version everywhere.

    Pitfall: Mixing project and system versions without checking.

The safe path, if you are not sure

  1. One project. Start with one project you know, not your whole disk.
  2. The system binary. Install the release archive from GitHub Releases and verify it against SHA256SUMS.
  3. The lean MCP profile. dctx mcp --profile lean exposes two tools, find and read, with compact descriptions.
  4. Measure. Run the same task with grep plus file reads and with dctx; compare whole-session tokens and calls, not only answer size.

Then pick the path above that matches your work. Choosing how to use dctx compares every mode with grep plus file reads.

Two scopes, one binary

  • System binary: the dctx on PATH belongs to you and your agents, and you upgrade it. Interactive agents and MCP call this one.
  • Project binary (with the Python, Node and Go wrappers, registry publication pending): a binary installed by a project library lives inside that project (virtualenv, node_modules), pinned and managed by that package manager. Application code and CI call this one; a library never silently falls back to PATH.
  • Same engine, different owner. dctx doctor lists every binary in reach; verify each against SHA256SUMS and its cosign signature.

Who is responsible for what

Each level of use has its own responsibilities. dctx provides the left column; the right column is yours.
