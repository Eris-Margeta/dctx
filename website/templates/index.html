Templates

Templates

The dctx Template System (DTS) defines the text dctx pack prints. dctx 1.3.1 ships two built-in templates; both are shown here with their real output on the sample project.

Which template pack uses

dctx pack renders the default template; --tree-stamps=on selects the stamped one, the 1.0.0 text. legacy_output.rs dctx template build <PATH> parses and validates a template file and prints its compiled plan; with --output PATH it writes the plan. dctx template list lists explicit compiled plans. The 1.1.0 pack command has no option that selects a compiled plan, so this page shows no third, custom template.

What changes between them

This file defines how the LLM context is formatted. The only difference is the tree entry and its instruction line: the default leaves out MOD and SIZE, because a timestamp changes on a bare touch and a size on every edit, and either breaks the byte-stable prefix a prompt cache reuses. Syntax

From ADR-003, sections 1, 3, 4 and 5. The contract of the source and the compiled plan is DTS v2.

1. Decision: Explicit Marker Definition#

To ensure future compatibility with non-HTML-like syntax, the templating language separates "Opening" and "Closing" logic for tags into four distinct definitions: * start_marker_open (Default: <) * start_marker_close (Default: >) * end_marker_open (Default: </) * end_marker_close (Default: >)

This allows users to redefine tags completely, e.g., to [SECTION] ... [/SECTION] or {{#SECTION}} ... {{/SECTION}}.

3. Decision: Two-Pass Rendering Engine#

The rendering engine operates in two distinct passes to separate Configuration from Data.

  • Pass 1 (Config Resolution): Occurs during the "Template Build" phase. Resolves all {{VAR}} placeholders within the [VARIABLES] section.
  • Pass 2 (Data Injection): Occurs during runtime. Injects {{{DATA}}} into the pre-compiled Partial structures ([PARTIALS] section) and assembles the [LAYOUT].

4. Template File Structure#

The file format uses a custom INI-like syntax with three specific sections: 1. [VARIABLES]: Key-Value pairs for static strings. 2. [PARTIALS]: Definitions for repeated elements (TREE_ENTRY, FILE_BLOCK). 3. [LAYOUT]: The global document structure.

5. Available Data Variables (Runtime)#

These variables are populated by the Rust core: * {{{node.id}}}: Optimized incremental ID (e.g., 1, 2, 10). * {{{node.path}}}: Relative path. * {{{node.type_char}}}: [D] or [F]. * {{{node.mod}}}: Unix timestamp in milliseconds. Available to custom templates. The built-in default template does not print it since 1.0.1, because a timestamp changes on a bare touch and breaks the byte-stable prefix of the page; --tree-stamps=on selects the built-in stamped template (the 1.0.0 text, MOD: and SIZE: on every tree line, MOD in the instructions). The default entry also leaves out {{{node.size_part}}}, since a size changes on every ordinary edit; {{{node.size}}} and {{{node.size_part}}} stay available to custom templates. * {{{node.size}}}: File size in bytes. * {{{file.lines}}}: Line count of the file. * {{{file.content}}}: Actual file content.
